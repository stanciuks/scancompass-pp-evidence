7. A RUNBOOK STEP THAT COULD NOT RUN AT ALL, AND THE CHOSEN RESOLUTION

The deployment step began "fetch from the origin and check out the commit".
THAT CANNOT WORK ON THIS SERVER, and the failure is not transient: the
repository is private, the server holds no credential helper, and the fetch
fails for want of a username. The commit was simply unknown to the server. This
also explains why the checkout had been stale since M12C — the server has never
been able to pull. [R1,R2]

THE RESOLUTION CHOSEN WAS A VERIFIED GIT BUNDLE, built on the build host from
the proven clone and carried to the server. IT INSTALLS NO CREDENTIAL ON THE
SERVER, git verifies every object hash on fetch, and the checkout is pinned by
commit identifier, so it is as trustworthy as fetching from the origin and more
auditable. The bundle's SHA-256 was verified identical on both hosts and the
bundle verified on the server before anything was fetched. [R1,R2]

THE ALTERNATIVE — GIVING THE SERVER A READ-ONLY DEPLOY CREDENTIAL — WAS LEFT AS
AN OWNER DECISION rather than taken quietly under deployment pressure. [S2]

13. THE OPERATIONAL FOLLOW-UP THAT IS STILL OPEN

THE SERVER'S WORKING TREE IS STILL DIRTY AND STILL STALE, and it was
deliberately not tidied as a side effect of a deployment. Why it still matters,
stated rather than softened: [S2]

  - the rollback procedure READS AN OPERATOR SQL FILE FROM THAT TREE, where it
    is untracked. A clean would delete it and a checkout could change it —
    either would break rollback at the moment it is needed;
  - the server cannot fetch from the origin, so the tree cannot be reconciled
    by the obvious command and will keep drifting;
  - a clean tree is a precondition in two runbook steps, and it cannot pass
    while the tree is dirty.

Reconciling it is a SEPARATE, DELIBERATE OPERATION with its own review, and it
needs a decision first: whether the server receives a read-only deploy
credential or keeps receiving verified bundles. [S2]
