8. THE RELEASE PROCEDURE, AND THE SIX TIMES IT WAS WRONG

The page was finished on 13 October. Everything after that is about how to put
it into production without breaking a running site.

The procedure was written as a numbered set of blocks, each pasted into a server
terminal as one unit. Each block runs with the shell set to abort on any error,
each writes a success marker only if it actually passed, each refuses to run
unless the blocks it depends on have left their markers, and the ones that run
after the application has been changed must write an attempt marker BEFORE they
judge anything. If a block fails after the switch, it records that state
permanently and from then on every block except the rollback refuses to run.
That design was not there at the start. It is what six rounds of review forced.
[S2,V1]

                                  integrity unproved; the base image was not

9. THE 15 OCTOBER PRODUCTION STOP

The first real production attempt ran under an owner-approved window and an
authorisation bound to that run. The early read-only checks passed: the
application, database and scanner were healthy, the running image was the
expected one, the scanner and maintenance images were unchanged, all three
payment flags were 0, no provider value and no payment-era marker existed,
health answered locally and publicly, all fourteen payment routes answered 404,
/plans answered 404, persistence was READY on m13-0004, payments were DISABLED,
and the database audit passed with 18 checks and reported ERA 1. [R1]

THEN THE PROCEDURE STOPPED, AND IT WAS WRONG TO STOP.

The reconciliation check read a report that states the payment era, and required
a line reading exactly "ERA 1". The database said ERA 1. But the report is
produced in the database client's default aligned table format, which pads the
value, so the line actually read " ERA 1" with a leading space. The check
demanded an exact whole-line match and rejected a correct database. [R1,S2]

THE REASON THE TESTS NEVER CAUGHT IT IS WORTH RECORDING. The test harness used a
fake database client, and the fake printed the line without padding. The check
and the fake agreed with each other, not with PostgreSQL, and every revision
since the check was added inherited that agreement. A test is only as good as
the thing it stands in for. [S2]

Nothing was forced. No success marker was written, no image was transferred, no
later block ran, and the running application was confirmed untouched, still on
its original container from the earlier production deployment. One earlier
interactive paste of the block had been corrupted and had stopped; the block was
then re-run from a hash-verified file and reproduced the same stop. [R1]

The fix was written test-first. The new cases were run against the old procedure
and 13 of them failed, which is the point of writing them first. Two of those
failures mattered:

  - the padded line was refused at the live check, with production's exact
    message, reproducing the stop;
  - A SECOND, OPPOSITE DEFECT CAME OUT AT THE SAME TIME. Had the output not
    been padded, the old check would also have ACCEPTED a report that contained
    ERA 1 together with ERA 2, or ERA 1 twice. The strict check was
    simultaneously too strict about spaces and far too lax about what else the
    report could say. [S2]

The corrected check accepts the report only if it holds exactly one era value
line and that line is exactly ERA 1, with surrounding spaces or tabs allowed.
Anything else, including a failed database run, stops the release. On the
corrected procedure the new cases passed, the full server-block run passed 1,216
checks with none failing against the previous revision's 1,118, the build-host
run passed 128, and 12 of 12 targeted mutations of the fixed code were killed.
[S2]

A separate reviewer reproduced the padded ERA-1 output against PostgreSQL
with the project's own migrations applied. The ERA-1 and SQL-error outputs
matched the corresponding fixtures byte for byte. The ERA-2 fixture was not
validated as a real capture (see section 11). [V1]

THE FIX HAD A PRICE. Changing the shared library changed its hash, and the whole
authorised run was bound to that hash. Nothing from the stopped run carried
over: not the build record, not the server run directory, not its run identifier,
not the authorisation. The server-side preparation and the entire sequence of
baseline checks had to be done again from the beginning, in a new directory,
under a new authorisation. That is the correct behaviour of a procedure bound to
hashes, and it is also why a one-character formatting bug cost a day. [S2,V1]

ONE FINDING FROM THAT OFFLINE WORK IS THE MOST INSTRUCTIVE THING IN THE WHOLE
PACKAGE. The preflight sanitises its own environment by re-executing itself in
an empty one. But the command it uses to do that can itself be shadowed by an
inherited shell function of the same name, in which case the sanitised child is
never started at all. It was reproduced on 19 October against the exact
preflight script: a forged function printed two convincing lines, including a
confirmation that the pinned library had been verified, and exited 0 HAVING
CHECKED NOTHING. Launched instead from a deliberately empty environment, by
absolute path, with the shell told to read no startup files, the same file ran
the real preflight and stopped where it should. [R3]

TWO HONEST CONSEQUENCES ARE RECORDED WITH IT. No case in the test matrix covers
that hole, and the script's own header comment still carries the claim that the
command cannot run a shell function, WHICH IS WRONG AND WAS LEFT IN PLACE so
that the script's reviewed hash would not change. The hole was closed in the
LAUNCH PROCEDURE instead, which is why the owner's authorisation required the
empty-environment launch and why the preflight's first reported section is that
its environment is clean. A script cannot certify the shell it is already
running in. [R3,O1]
