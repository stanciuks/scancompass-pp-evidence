STEP 13 PURPOSE
Step 13 reconciled the public legal/privacy representation and operator documentation with the
actual M11 source implemented in Steps 4–12.

The main reason for the step was a real privacy-copy defect:

Before Step 13 the public scanning-policy page said, in substance:

- an assessment is not written to a database;
- there is no permanent link to a report;
- nothing survives a restart.

Those statements were still true of the current deployment only because no DATABASE_URL had been
configured yet.

They were already false of the source after Steps 7–12, because the repository contained:

- a durable persistence write path;
- durable report rows;
- share links;
- report delivery rows;
- retention/purge code.

If Step 15 had provisioned PostgreSQL without correcting the public wording first, the published
privacy representation would have silently become false.

Step 13 therefore corrected the wording before provisioning.

FROZEN ARTIFACT VS DOWNLOAD
An important Step 13 correction separated two contracts that an earlier draft had conflated.

STEP 6:
The frozen PublicAssessmentReport artifact is stored as:

- exact serialized report bytes;
- byte size;
- SHA-256 digest over exactly those bytes.

STEP 10:
A download is NOT those same stored bytes.

The share resolver verifies the frozen artifact, then Step 10 renders a NEW standalone HTML file
from that verified frozen report using react-dom/static prerender.

Therefore:

- report data/semantics are frozen;
- the stored artifact bytes are exact and hash-verified;
- the downloadable HTML file is a new rendering from the frozen report.

The public copy and tests were corrected so they no longer say or imply that the download is
byte-identical to the stored artifact.

RETENTION WORDING
Step 13 deliberately does NOT say:

30 days, then deleted.

The final public wording reflects the real retention policy:

Default anonymous retention:
30 days

Share default lifetime:
30 days

Absolute anonymous maximum:
90 days from the original scan creation time

The ceiling is non-rolling.

Repeated share creation cannot move a report past the 90-day ceiling.

Expired records are removed by the bounded retention process rather than being promised to vanish
at the exact instant expires_at is reached.

SHARE / REVOCATION WORDING
The public copy states:

- a share URL is a bearer capability;
- anyone with a valid live share URL can resolve the report;
- share and management capabilities are separate secrets;
- they are not intentionally stored in readable plaintext form;
- the server stores one-way digests;
- scanId is not an authorization credential;
- revocation stops future successful resolution;
- revocation cannot retract a report that was already viewed/downloaded or already in flight.

It does not call the management capability the only route to deletion because operator purge also
exists.

EMAIL PRIVACY WORDING
The final public copy states that email delivery:

- ships disabled;
- is available only when an operator explicitly enables it with valid configuration;
- transmits the recipient address to the configured external email-delivery provider;
- necessarily gives that provider the recipient address;
- may involve provider-side processing/retention under that provider's own terms/service practices;
- does not give SCANCOMPASS control over provider-side retention;
- does not intentionally store the recipient address in plaintext;
- stores a keyed one-way digest used to recognise the same normalized address under the same key
  generation and enforce per-report delivery duplication/limits.

It does NOT claim:

- GDPR compliance;
- a certification;
- memory zeroization;
- immediate provider deletion;
- a provider retention period that has not been verified;
- recipient data is never retained anywhere;
- encryption-at-rest guarantees not implemented by the application.

The recipient HMAC key is required for READY email configuration.

Generation command documented:

The command was empirically verified against the real parser:

The actual key value was not recorded in the evidence.

HMAC KEY LOSS / ROTATION
A first Step 13 draft incorrectly said losing/rotating EMAIL_RECIPIENT_HMAC_KEY did not break
delivery.

This was corrected.

Final documented behavior:

- missing/invalid HMAC key => email UNAVAILABLE;
- a valid replacement is required before READY can return;
- routine rotation is unsupported during M11 while rows written under the old key can remain;
- the single key generation is identified as v1;
- anonymous rows have a maximum 90-day lifetime;
- an emergency replacement inside that period changes the recipient digest identity;
- the same address for a still-live scan may therefore fail to collide with its old digest and may
  receive a second email;
- hmac_key_id distinguishes generations but does not restore cross-key duplicate suppression.

Operator guidance:
back up the key and do not rotate it routinely during M11.
