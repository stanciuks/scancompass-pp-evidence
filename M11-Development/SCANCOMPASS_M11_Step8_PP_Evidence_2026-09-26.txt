PURPOSE
Give the caller who obtained a durable report an anonymous management capability
without turning scanId into a credential, requiring an account, storing the raw
capability, or putting the secret in a cookie, URL, cache entry, log, or database.

LIVE PERSISTENCE — FOUR BUSINESS PHASES
Step 8 extends Step 7 from three business INSERT phases to four:

BEGIN
1. INSERT scans
2. bulk INSERT scan_findings
3. INSERT scan_reports
4. INSERT report_management_tokens
COMMIT

The management-capability row is inside the SAME transaction as the durable report.

If management-token insertion fails before COMMIT:
- the entire transaction rolls back;
- the complete assessment/report is still returned;
- persisted:false;
- no scanId;
- no managementToken.

No capability-count query is used on the LIVE path because the new scan UUID is
fresh inside the transaction and cannot already have management-token rows.

Both COMPLETED and PARTIAL mint the initial capability.
PARTIAL remains PARTIAL.

TOKEN ENTROPY AND WIRE FORMAT
Token source:
randomBytes(32)

Entropy:
256 bits

Wire encoding:
unpadded base64url

Exact wire length:
43 ASCII characters

Allowed alphabet:
[A-Za-z0-9_-]

DIGEST CONTRACT
Stored digest:
SHA-256 over the RAW 32 random bytes

Stored as:
32-byte PostgreSQL bytea

The raw token is never stored in PostgreSQL.

SECRET HANDLING
The raw token is returned only in the successful /api/scan response that minted it.

A server-only SecretValue wrapper was added. The raw value is held outside the
object's own properties in a module-private WeakMap.

Ordinary disclosure paths are redacted:
- String(secret)
- template interpolation
- JSON.stringify
- util.inspect
- structured pino logging
- object spread

They yield:
[redacted]

The one explicit disclosure function is:
reveal(secret)

A boundary test proves the only production caller is the /api/scan transport boundary.

SCAN ID
scanId remains a correlation identifier and authorises nothing.

PUBLIC RESPONSE SEMANTICS
LIVE acknowledged COMMIT:
persisted:true
scanId present
managementToken present

LIVE definite non-persistence:
persisted:false
no scanId
no managementToken

LIVE COMMIT outcome unknown:
persisted:null
no scanId
no managementToken

On COMMIT ambiguity, PostgreSQL may have committed the capability row, but the raw
token is discarded. Such a row is inert because nobody received the secret.

RECENT_CACHE MANAGEMENT CAPABILITY
A RECENT_CACHE hit with persisted:true and a scanId may mint a DISTINCT management
capability for the current caller.

Reason:
Visitor B can receive visitor A's cached report. Reusing A's management capability
would let B later manage/revoke objects created by A.

A cache hit remains free of:
- outbound assessment;
- global scanner capacity;
- the per-target outbound scan lock.

It may perform bounded database work solely to mint the caller's management
capability.

CACHE-HIT CAP
Maximum management-token rows per durable scan:
100

The bound is exact.

Cache-hit transaction:

BEGIN
SELECT scan row FOR UPDATE
SELECT count(*) management tokens for scan
if count >= 100:
  complete transaction without writing
else:
  INSERT report_management_tokens
COMMIT

The row lock is taken before count, so two callers starting at 99 cannot both create
rows 100 and 101.

This row cap is not itself a request-rate limit.

The existing edge controls continue to limit /api/scan:
- per-IP: 3 requests/minute, burst 2
- global: 24 requests/minute, burst 6

CACHE CONTENT
The result cache never stores:
- raw management token
- token digest
- token-row id

cacheableDurability() strips a LIVE caller's capability before caching.

CACHE-HIT FAILURE SEMANTICS
A cache-hit mint is additive to an already-durable report.

If minting fails because of cap reached, database failure, breaker open, scan
missing/expired, timeout, COMMIT outcome unknown, or a local generation fault:
- persisted:true remains true;
- existing scanId remains;
- managementToken is omitted;
- no 5xx is produced.

TTL
The management capability expires exactly when its owning scan expires.

LIVE:
expiresAt = scans.expiresAt

RECENT_CACHE:
expiresAt = expires_at read from the locked scans row

It is not recomputed as mint time + 30 days.

CIRCUIT-BREAKER REVIEW DEFECT
Independent review found a real defect in the first Step 8 candidate.

A local CSPRNG/UUID/clock failure could occur after the breaker claimed its single
HALF_OPEN probe slot. Because only recordSuccess()/recordFailure() release that
slot, the process could become stuck in HALF_OPEN and skip every future persistence
attempt.

Correction:
All potentially-throwing local capability material is prepared BEFORE the breaker
is claimed.

A local preparation failure now returns INTERNAL_ERROR with:
- no connection;
- no breaker success/failure verdict;
- no HALF_OPEN probe claimed.

Tests prove the next eligible caller can still become the probe and recover the
breaker to CLOSED.

WRITE-BUDGET REVIEW DEFECT
Independent review found a second real defect.

The shared transaction checkpoint originally tested only whether the scheduled
deadline callback had fired. The monotonic budget could already be exhausted while
the timer callback was still waiting, allowing another statement to start after the
intended deadline.

Correction:
checkpoint() now refuses when either:
- the timer has fired; OR
- remaining() <= 0.

A deterministic test arms the timer but deliberately never fires it, advances the
monotonic clock past the budget, and proves the next statement does not start.

The Step 7 invariant remains:
timeout before COMMIT => definite non-persistence.

SHARED TRANSACTION MACHINE
Step 7's bounded transaction / COMMIT ambiguity logic was extracted into:
src/server/persistence/write/transaction.ts

It is intentionally shared by:
- whole-assessment persistence
- cache-hit capability minting

This avoids two copies of the most subtle state machine in the persistence layer.

The extraction was explicitly accepted during independent review.

COMMIT ON CAP
A cache-hit attempt that reaches the 100-token cap after only SELECTs completes its
transaction with COMMIT rather than a special ROLLBACK.

This was independently reviewed and accepted.

CANONICAL INPUT CONTRACT — STEP 9
Step 9 must accept an untrusted management token only if:

1. exactly 43 characters
2. matches ^[A-Za-z0-9_-]{43}$
3. base64url-decodes to exactly 32 bytes
4. re-encoding those bytes to unpadded base64url reproduces the exact supplied string
5. SHA-256 is computed over the decoded raw bytes

Step 8 deliberately does NOT implement an unused verifyManagementToken() resolver.
