READINESS ARCHITECTURE
Four new persistence modules:

- schema-contract.ts
  Code-owned structural contract for the database shape this application image
  requires.

- readiness-status.ts
  Pure, total classification logic. No pg import.

- probe.ts
  One bounded, read-only, short-lived pg.Client probe.

- readiness.ts
  Wires config -> probe -> classification and exposes safe startup log fields.

The existing src/instrumentation.ts is the sole composition point between:
- launch readiness
- persistence readiness

The two readiness systems do not import each other.

ZERO-LEDGER-ACCESS DECISION
The application role keeps zero privileges on:
scancompass.schema_migrations

Step 5 therefore does NOT claim to know the database's exact applied migration
version.

Instead it checks structural compatibility against:
EXPECTED_SCHEMA_CONTRACT = "m11-0000"

Meaning:
this application image requires the m11-0000 structural contract.

It is not:
- an observed migration version
- proof that 0000 is the latest applied migration
- read from the migration ledger

STRUCTURAL COMPATIBILITY
The readiness contract covers:
- dedicated scancompass schema
- six application-data tables
- schema_migrations relation existence only
- scan_findings_id_seq
- required columns
- exact PostgreSQL types required by this image

The compatibility rule is one-directional:
everything this image requires must exist and be compatible.

Extra objects are not rejected merely for existing.

Step 5 explicitly does not claim every future additive migration is automatically
backward-compatible with an older writer. Actual future write compatibility
remains a migration-design and Step 7 writer-test obligation.

TLS OBSERVATION
Live-session encryption is observed separately from configured sslmode using:

SELECT ssl
FROM pg_catalog.pg_stat_ssl
WHERE pid = pg_backend_pid();

Configured mode and observed encryption are not conflated.

For require / verify-ca / verify-full:
- observed TLS false -> UNAVAILABLE / TLS_REQUIRED_NOT_OBSERVED
- TLS unmeasurable -> UNAVAILABLE / TLS_OBSERVATION_UNAVAILABLE

For disable / prefer / unspecified:
- TLS observation remains diagnostic and does not by itself make readiness fail.

BOUNDED PROBE
Short-lived pg.Client, never a process-lifetime pool.

Code-owned bounds:
- connectionTimeoutMillis: 2000 ms
- query_timeout: 2000 ms
- whole-probe backstop: 4500 ms

Other properties:
- no retry
- no polling
- no recurring health task
- three SELECT-only probe stages
- no DML
- no DDL
- no transaction
- active client closure on total-budget expiry
- client.end() cleanup in all paths

DETACHED STARTUP
Persistence readiness is started after the existing launch-readiness logs and is
NOT awaited by instrumentation.register().

Therefore PostgreSQL cannot delay:
- Next startup
- free scan availability
- launch-readiness logging

The detached task handles all rejections.

Exactly one persistence_readiness result is logged per startup in normal,
expected-failure, unexpected-rejection and unexpected-synchronous-throw cases.

The fallback payload is code-owned and contains no raw Error.message, stack,
hostname, database, username, password or connection URL.

FAILURES / CHANGES DURING STEP 5
1. Step 4 left docs/ARCHITECTURE.md stale and still describing the pre-persistence
   repository. Step 5 corrected it.

2. The design originally said readiness verifies "schema version", but the app
   role intentionally cannot read schema_migrations. Step 5 switched to honest
   structural compatibility and an application-owned contract id.

3. NOT_CONFIGURED was narrowed to genuine absence of DATABASE_URL. A present but
   invalid config is UNAVAILABLE / CONFIG_INVALID.

4. DEGRADED is deliberately not produced in Step 5 and is reserved for Step 7.

5. The startup persistence probe was made detached rather than awaited, so DB
   failure cannot delay the free scanner.

6. The planning report initially described 11 launch controls. Inspection showed
   the unchanged pre-Step-5 inventory has 12; all 12 are now explicitly pinned.

7. The first unexpected-failure fallback log omitted configuredSslMode, used a
   non-code-owned "unknown" contract id, and risked a double log if the normal
   logger threw. The fallback was corrected and mutation-tested.

8. Structural-compatibility wording was tightened so the project does not claim
   arbitrary future additive migrations are automatically compatible.

9. A doc comment in readiness.ts used a migration-role environment-variable name
   that violated an existing boundary rule; the wording was corrected.

10. probe.ts intentionally connects only inside the explicit readiness function,
    which tripped a broad import-time-network structural rule. A narrow documented
    exemption was used and paired with stronger tests that unconfigured readiness
    opens zero connections.

11. No production state changed during Step 5.
