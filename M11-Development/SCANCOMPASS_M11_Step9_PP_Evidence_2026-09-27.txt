STEP 9 PURPOSE
Step 9 implements the first real use of the anonymous management capability created in
Step 8 and adds bearer-capability report sharing without accounts.

The design goals were:
- scanId remains a non-secret correlation identifier and authorises nothing;
- management capability verifies management operations;
- share capability is a separate secret;
- raw bearer tokens are not stored in PostgreSQL;
- share tokens are never placed in path/query/cookie/log;
- public report display comes only from the frozen persisted artifact;
- share resolution performs zero database writes;
- no viewer analytics are introduced.

MANAGEMENT-CAPABILITY VERIFICATION
Canonical incoming capability contract:

1. exactly 43 characters
2. alphabet:
   [A-Za-z0-9_-]
3. strict base64url decode
4. exactly 32 decoded bytes
5. re-encode to unpadded base64url
6. re-encoded value must equal supplied value exactly
7. SHA-256 is computed over the decoded RAW 32 bytes

The verifier:
- looks up by unique management_token_hash;
- checks stored digest length before comparison;
- uses crypto.timingSafeEqual;
- checks revoked_at;
- checks capability expires_at;
- checks owning scan expires_at;
- does not accept scanId from the caller.

Public authorization failures remain neutral.
A caller is not told whether the token was malformed, unknown, revoked, expired or attached
to an expired report.

failed_attempts POLICY
report_management_tokens.failed_attempts remains inactive.

Reason recorded in the implementation:
- an unknown guessed token matches no row, so no per-row counter can count guessing;
- a matched row means the caller already knows the 256-bit capability;
- lockout would mainly create self-denial-of-service risk.

No Step 9 module increments the field.

SHARE TOKEN
Share token source:
randomBytes(32)

Entropy:
256 bits

Wire format:
unpadded base64url

Exact length:
43 characters

Stored form:
SHA-256 over the raw 32 random bytes

The raw share token is disclosed once in the successful share-create response.
It is not stored in PostgreSQL.

SHARE RETENTION
Binding Step 9 retention policy:

DEFAULT_SHARE_TTL_DAYS = 30
ANONYMOUS_ABSOLUTE_MAX_DAYS = 90

The 90-day maximum is measured from the ORIGINAL scan creation time.

It is not a rolling 90-day extension from share creation.

Rules:

absoluteMax =
scan.createdAt + 90 days

candidateShareExpiry =
now + 30 days

shareExpiresAt =
min(candidateShareExpiry, absoluteMax)

newScanExpiresAt =
max(existingScanExpiry, shareExpiresAt)

newScanExpiresAt can never exceed absoluteMax.

Consequences:
- a normal new share can live up to 30 days;
- a share created near day 90 is shortened honestly;
- repeated share creation cannot keep an anonymous scan indefinitely;
- no ttlDays request field exists in Step 9.

CREATING MANAGEMENT-CAPABILITY EXPIRY
When a share extends beyond the creating management capability's current expiry, Step 9
extends only that creating capability.

The current capability row is re-read under the scan-row lock before extension.

This prevents:
- using a stale verifier copy;
- shortening a concurrent extension;
- making the share outlive the capability that must be able to revoke it.

Other management capabilities for the same scan are not extended.

SHARE CAP
MAX_SHARES_PER_SCAN = 5 TOTAL rows.

The count includes:
- active rows
- expired rows
- revoked rows

Revocation does not free a slot.

Reason:
the cap is an at-rest growth bound. If revoked rows stopped counting while remaining stored,
a caller could create/revoke indefinitely and the five-row cap would not actually bound the
table.

SHARE CREATE
POST /api/reports/share

Request body:
{ managementToken }

High-level flow:
management capability
-> canonical parse
-> management verification
-> generate share token and row id
-> begin bounded transaction
-> lock scans row
-> re-read creating management capability
-> count all report_shares rows
-> enforce five-total-row cap
-> calculate bounded retention
-> insert report_shares
-> extend scan expiry if required
-> extend creating management capability if required
-> COMMIT
-> return raw share token exactly once

COMMIT ambiguity:
If COMMIT is sent but not acknowledged:
- return service unavailable;
- do not return the raw share token;
- a possibly committed row is inert because nobody received the secret.

SHARE REVOKE
POST /api/reports/share/revoke

Request body:
{
  managementToken,
  shareId
}

Database security boundary:
UPDATE report_shares
WHERE
  id = supplied share id
  AND created_by_management_id = verified management row id
  AND revoked_at IS NULL

After a valid management capability:
- one changed row -> 200 {ok:true}
- zero changed rows -> the same 200 {ok:true}

Zero rows may mean:
- unknown share id
- already revoked
- created by another management capability

Those states remain indistinguishable to the caller.

Revocation is soft:
revoked_at = now

Revocation is idempotent.
The design explicitly records that one autocommit UPDATE can still have an ambiguous
acknowledgement outcome; retry safety comes from idempotency, not from claiming that one
statement is unambiguous.

SHARE-ID CONTRACT
The browser mirror and revoke route now consume one client-safe share-id validation contract.

This was introduced after review found that a generic 8-4-4-4-12 hex regex was broader
than the route's UUID acceptance.

The final shared contract:
- accepts the UUID class the system can actually mint;
- rejects invalid version/variant shapes;
- is used by both browser mirror validation and route validation.

Regression tests include UUID-shaped hex strings that are not valid under the route contract.

SHARE RESOLUTION
POST /api/reports/resolve

Request:
{ token }

Flow:
canonical parse
-> raw-byte SHA-256
-> bounded database read
-> report_shares JOIN scans JOIN scan_reports
-> stored digest length check
-> timingSafeEqual
-> share revoked/expiry check
-> scan expiry check
-> release DB connection
-> verifyReportArtifact()
-> return verified frozen report

The resolver:
- does not query scan_findings for presentation;
- does not recompute score/findings;
- performs zero writes;
- records no view count;
- records no last-viewed timestamp;
- produces no ordinary successful-view analytics log.

Artifact-integrity failures remain a neutral public refusal while an operator-safe integrity
event may be emitted.

FRAGMENT SHARE URL
Public share URL form:

/r/#<share-token>

The fragment is not transmitted in the HTTP request.

Browser sequence:
1. hydrate generic /r shell
2. read location.hash
3. cheap client shape check
4. capture token in non-rendered memory
5. immediately call history.replaceState(..., "/r/")
6. POST token in body to /api/reports/resolve
7. render only the verified returned report

The order is intentional:
replaceState occurs before fetch.

This removes the token from the visible address bar before waiting on network resolution.

The share token is retained only in a non-rendered in-memory ref for the lifetime of the
share page so Step 10 can later reuse the same bearer capability for native form POST
download.

The share token is not persisted to:
- sessionStorage
- localStorage
- cookies

A terminal authorization refusal clears the in-memory share token.

A temporary 503 keeps the token in memory and the interface now provides a Retry control
that reuses the same token without restoring the fragment.

GENERIC SHARE SHELL
The /r server response is:
- token-independent
- report-independent

It is deliberately not described as byte-identical because each document carries a
per-request CSP nonce.

The shell contains no token, no report data and no scan identity.

BROWSER MANAGEMENT-CAPABILITY OWNERSHIP
Review found a major bug in the first candidate:
- raw management capabilities were stored in React state;
- the complete secret-bearing list was also kept in React state;
- sessionStorage was effectively the source of truth;
- blocked storage could cause the capability/share creator association to disappear.

Final design:
- raw management capability list lives in a non-rendered useRef;
- React state contains only non-secret display metadata;
- a newly minted token arrives via a one-time callback backed by a ref;
- sessionStorage is best-effort mirror only;
- store mutation functions operate over the caller-supplied in-memory list;
- blocked storage does not break create/revoke behavior.

Multiple management capabilities per scan are supported.

Reason:
a live scan and a later cache hit can mint distinct management capabilities, while
revocation is scoped to whichever capability created a share.

Rules:
- newest capability creates new shares;
- older capability is retained while it owns locally-known shares;
- revoke uses the capability that created that share;
- obsolete capability with no known shares may be pruned.

The sessionStorage mirror stores management capabilities and share identifiers/expiries but
never share bearer tokens.

REQUEST BODY BOUND
Step 9 initially read report request bodies before checking declared size.

Final implementation matches the established /api/scan posture:
- declared Content-Length above the report ceiling is refused before request.text();
- actual UTF-8 byte length is checked after reading because Content-Length can be absent or
  incorrect.

Public report endpoint request schemas remain strict.

RESPONSE / REFERRER HEADERS
Final Step 9 header ownership was reconciled so the effective policy is explicit.

Relevant surfaces:
- ordinary document -> strict-origin-when-cross-origin
- /r -> no-referrer
- /api/scan -> strict-origin-when-cross-origin
- /api/health -> strict-origin-when-cross-origin
- /api/reports/* -> no-referrer

/r and report APIs also use:
- Cache-Control: no-store
- X-Robots-Tag: noindex, nofollow

The implementation explicitly records:
URL fragments are not included in Referer by browser behavior.
Referrer-Policy: no-referrer is the privacy posture for the share surface; it is not the
mechanism that keeps the fragment token secret.

CIRCUIT BREAKER / LOCAL-FAILURE CORRECTIONS
Several review rounds found lifecycle defects around HALF_OPEN recovery.

The important invariant:
a local clock/CSPRNG/UUID/timer defect is not evidence of PostgreSQL ill health and must not
strand the single HALF_OPEN probe.

Final implementation added a neutral breaker action:
releaseProbe()

This returns the HALF_OPEN probe slot without recording success or database failure.

The shared connection lifecycle now handles:
- local failure while arming the deadline;
- injected timer setup failure;
- monotonic-clock failure before/mid operation;
- local failure after BEGIN/statements but before COMMIT;
- post-body bounded-read deadline check;
- final pre-COMMIT budget/local-failure gate.

Final pre-COMMIT handling:
runBoundedTransaction() uses the shared checkpoint immediately before COMMIT.

If a local clock fails there:
- COMMIT is not sent;
- the open transaction is destroyed and rolled back;
- result is local/internal, not database failure;
- HALF_OPEN probe is returned without a DB-health verdict.

If the budget is genuinely exhausted there:
- it remains a timeout;
- COMMIT is still not sent.

This distinction was regression-tested.
