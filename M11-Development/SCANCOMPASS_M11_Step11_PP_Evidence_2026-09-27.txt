STEP 11 PURPOSE
Step 11 is the first SCANCOMPASS source step that implements durable deletion.
It adds:
1. routine expiry cleanup based on the stored scans.expires_at value;
2. operator-only denylist/opt-out purge for durable scans already stored.
No public retention, purge, admin, or DELETE route was added.

PARENT-ONLY DELETION
The only direct deletion target is scancompass.scans.
The five child tables are removed through ON DELETE CASCADE:
- scan_findings
- scan_reports
- report_management_tokens
- report_shares
- report_deliveries

This matches the least-privilege grant model: the application role has DELETE on scans and no direct child-table DELETE privilege.

SHARE GROWTH INVARIANT
MAX_SHARES_PER_SCAN = 5 counts all share rows for a scan, including active, expired, and revoked rows.
Step 11 therefore never independently deletes expired/revoked report_shares while their parent scan remains alive. Doing so would free slots and weaken the existing lifetime row bound.

RETENTION ELIGIBILITY
Normal expiry uses the row's stored scans.expires_at and the inclusive predicate:
expires_at <= capturedNow
It does not recalculate eligibility from created_at plus current configuration. This preserves Step 9 share extensions and avoids retroactively reinterpreting rows if policy values later change.

RUNTIME BOUNDS
RETENTION_BATCH_SIZE = 200
MAX_RETENTION_BATCHES_PER_RUN = 10
Maximum parent scans per invocation = 2,000.

The first candidate exposed test overrides without enforcing the production envelope. Review found that values such as batchSize=1,000,000 or maxBatches=1,000 could bypass the intended safety bound; maxBatches=0 could even return a successful-looking no-op.

Final production functions validate before any DB statement:
- finite integer
- batchSize 1..200
- maxBatches 1..10
Invalid values return INCOMPLETE / LOCAL_ERROR, deletedScans=0, batches=0, with zero DB calls. Values are refused, not silently clamped.

PERFORMANCE CLAIM
The 200-parent batch is a bounded starting value selected from cascade-amplification analysis. It is intended to fit the existing 2,000 ms statement_timeout, but real-PostgreSQL acceptance has not run and must confirm that. If 200 is too large, the approved correction is to reduce RETENTION_BATCH_SIZE, not widen the timeout merely to preserve the batch size.

ROUTINE EXPIRY LOCKING
Expiry uses FOR UPDATE SKIP LOCKED.
This lets routine cleanup yield to user-facing share operations. If a share transaction already owns the scan-row lock, expiry skips that row and a later run sees the resulting expiry state. If expiry deletes first, the later share operation observes SCAN_ABSENT.

EXPIRY DOES NOT CLAIM GLOBAL COMPLETION
Because SKIP LOCKED can skip eligible rows, a short or zero expiry batch does not prove that the database contains no expired rows. The expiry result therefore reports only invocation facts:
- deletedScans
- batches
- batchLimitReached
It deliberately has no global completed/mayHaveMore claim.

OPT-OUT PURGE LOCKING
The denylist purge deliberately uses blocking FOR UPDATE without SKIP LOCKED.
It completes only after a blocking batch finds zero matching rows. If it meets a held lock it waits; if the wait exceeds statement_timeout it returns INCOMPLETE / QUERY_TIMEOUT and is safe to retry. This avoids falsely telling an operator that an opt-out purge completed while a locked matching row remained.

DENYLIST-DRIVEN PURGE
The purge is not a generic arbitrary-host deletion tool. Before opening persistence it reads the active SCAN_DENYLIST_FILE and requires the exact configured rule pair:
{ scope, canonicalHostname }
Approved scopes:
- EXACT_HOST
- DOMAIN_AND_SUBDOMAINS
An EXACT_HOST rule does not authorize the broader DOMAIN_AND_SUBDOMAINS purge for the same hostname.

RUNTIME SCOPE REVIEW FINDING
PurgeScope is compile-time only. An early predicate treated any runtime value other than EXACT_HOST as the broader subdomain scope. Review identified this as unsafe. Final code checks the two approved values at runtime before any statement; anything else returns CONFIG_INVALID with zero DB calls.

HOST MATCHING
EXACT_HOST: hostname = canonicalHost
DOMAIN_AND_SUBDOMAINS: hostname = canonicalHost OR hostname LIKE '%.canonicalHost'
Matching is label-safe and does not broaden to registrable-domain, effective website hostname, or mail assessment domain semantics.

OPT-OUT ORDERING
Documented operator order:
1. add denylist rule;
2. restart app;
3. verify the target is refused;
4. purge the exact active rule;
5. retry INCOMPLETE runs;
6. stop only on COMPLETED.
The denylist/restart comes first so a fresh durable row cannot be created between purge and activation of the opt-out. Restart also clears the process-local result cache.

IN-FLIGHT READ LIMIT
After purge commit, future share resolution and management verification refuse and new share creation cannot operate on the removed scan. A request that obtained the frozen report before deletion linearised may still finish its response. The durable guarantee begins at purge commit; the system cannot retract bytes already read/in flight.

DATABASE ROLE
Retention uses DATABASE_URL / the application role, never DATABASE_MIGRATION_URL. It performs no DDL and no migration-ledger work. No new credential or grant was added.

CIRCUIT BREAKER DECISION
Retention uses a short-lived pg.Client and no shared request-path circuit breaker. A one-shot maintenance process has no useful breaker history, and retention failure must not affect share/resolve request health. Scheduler cadence is the retry/backpressure mechanism.

CONFIGURATION REVIEW FINDING
The first connection implementation collapsed NOT_CONFIGURED and invalid configuration into one result. Final mapping:
- no DATABASE_URL -> NOT_CONFIGURED
- present but invalid persistence configuration -> CONFIG_INVALID
- valid config -> connection attempt
Tests cover malformed URL and invalid numeric persistence settings without leaking configured values.

CONNECT FAILURE TAXONOMY
Final behavior:
- ETIMEDOUT -> CONNECT_TIMEOUT
- exact uncoded pg 'timeout expired' -> CONNECT_TIMEOUT
- ENOTFOUND / EAI_AGAIN -> CONNECT_FAILED
- ECONNREFUSED / reset / TLS / authentication -> CONNECT_FAILED
Raw driver messages are not printed.

QUERY TIMEOUT ORDERING
An intermediate implementation used a fixed 10,000 ms client query_timeout. Review found that valid statement_timeout configuration can be up to 30,000 ms, so the client could fire first.
Final rule:
PURGE_QUERY_TIMEOUT_MARGIN_MS = 5,000
query_timeout = configured statement_timeout + 5,000 ms
Thus the client timeout remains strictly above every accepted server statement_timeout.

QUERY FAILURE TAXONOMY
- PostgreSQL 57014 -> QUERY_TIMEOUT
- ETIMEDOUT -> QUERY_TIMEOUT
- exact uncoded pg 'Query read timeout' -> QUERY_TIMEOUT
- ECONNRESET / EPIPE -> QUERY_FAILED
- ordinary query errors -> QUERY_FAILED
Coded errors are not reclassified merely because their message text resembles a timeout.

CLI EXIT SEMANTICS REVIEW FINDING
An early implementation printed expire INCOMPLETE reason=NOT_CONFIGURED but exited 0. That could let a future scheduler record a successful maintenance run that did no work.
Final rule:
Zero exit only for expire OK, purge-host COMPLETED, or explicit --help. Every incomplete/refused/failure state exits non-zero.
