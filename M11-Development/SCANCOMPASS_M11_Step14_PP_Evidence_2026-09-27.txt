CLIENT IDENTITY
The report limiter is keyed on $binary_remote_addr, the nginx-observed TCP peer address.

Current topology:
internet -> nginx -> loopback application

There is no CDN, upstream load balancer or RealIP rewriting in front of nginx. Therefore the limiter
key is the public TCP client address under the current architecture.

No client-controlled forwarding header is used as a limiter key.

The application trust boundary remains separate:
- nginx sets X-Site-Security-Client-IP from $remote_addr;
- nginx supplies the proxy trust token;
- generic forwarding headers remain stripped;
- Step 14 changes none of those server-level proxy_set_header directives.

REPORT API LOCATION

This location covers the five M11 report endpoints:

REPORT 429 SEMANTICS
The report prefix deliberately does not use @scan_rate_limited and no new report-specific application
error vocabulary was invented.

A report request rejected by nginx rate limiting receives nginx's native 429 response. It is refused
at the edge before Node/database/provider work.

No report-specific Retry-After requirement was added.

SHARED REPORT 429 CLIENT DEFECT
Independent Step 14 review identified a client-lifecycle defect that had to be fixed before the edge
limit could safely ship.

Before Step 14, SharedReportView treated 503 as temporary/retryable but treated every other
non-success response as terminal. The terminal branch cleared tokenRef and rendered the invalid-link
state.

After Step 14, nginx can legitimately return 429 for a valid share token. If unchanged, a temporary
rate limit would have been interpreted as an invalid/revoked/expired capability, destroyed the only
in-memory token, and made Retry impossible.

STEP 14 CLIENT FIX
SharedReportView now treats 503 OR 429 as temporary/unavailable.

On 429:
- tokenRef is retained;
- unavailable/retry UI is shown;
- Retry reuses the same capability;
- the fragment is not restored;
- no invalid-capability conclusion is made.

A genuine terminal authorization refusal still clears the token.

OTHER REPORT CLIENTS
ShareControls create/revoke discard management capabilities only on 404, so 429 already preserved the
capability. EmailControl falls through to generic unavailable wording and does not own/destroy the
management capability. No additional client changes were required.

DOWNLOAD 429
The native form POST download may navigate to nginx's ordinary 429 response when rate-limited. Step 14
deliberately does not redesign the download mechanism.

TLS-VS-HTTP TEST DEFECT
Independent review found a pre-existing false-positive test helper.

Both nginx suites used SITE.indexOf("location / {"). But site-security.conf has two root locations:
1. port-80 redirect location /
2. TLS application-proxy location /

The helper returned the first/port-80 block, so an assertion intended to prove ordinary HTTPS
browsing was unthrottled was actually checking the redirect server and passing for the wrong reason.

TEST FIX
The helper was corrected structurally.

Tests now identify the production TLS server from its listen 443 ssl http2; server block,
brace-balance that server, and resolve TLS locations within it. The HTTP redirect server remains
separately identified/tested.

The fix does not rely on first-occurrence or last-occurrence ordering.
