STEP 10 PURPOSE
Step 10 adds secure download of an already-authorised frozen shared report.

Flow:
share capability held in memory
-> same-origin POST body
-> existing Step 9 share resolver
-> verified frozen report artifact
-> self-contained HTML attachment

PUBLIC ENDPOINT
POST /api/reports/download

No GET download endpoint exists.

Request encoding:
application/x-www-form-urlencoded

Body:
token=<share capability>

The download endpoint reuses resolveShareCapability(token), so Step 10 adds:
- no second token parser
- no new SQL
- no new database transaction
- no scan_findings presentation read
- no database write
- no viewer analytics write

The database connection is released before rendering.

NATIVE DOWNLOAD / TOKEN HANDLING
The resolved /r page already holds the share token only in a non-rendered useRef.

The download uses a native same-origin form POST.

It does NOT use:
- fetch + Blob
- blob:
- URL.createObjectURL
- <a download>
- a download ticket
- a token in a URL/path/query
- localStorage
- sessionStorage
- cookies

The form has no token-bearing hidden input.

The browser formdata event adds the token directly to the submission FormData at submit time.

TEST-RUNTIME LIMITATION
jsdom 25 does not implement the real FormDataEvent/formdata lifecycle and requestSubmit()
cannot be used as a real browser submission.

The tests therefore verify the component seam without claiming browser E2E execution:
- form markup contains no token
- a controlled requestSubmit stub dispatches formdata synchronously
- submission FormData receives the token
- requestSubmit is called once
- listener is removed afterwards
- token remains absent from DOM/storage/cookie/URL

No browser E2E framework was added for Step 10.

REACT RENDERING DISCOVERY
The first implementation used renderToStaticMarkup from react-dom/server.

Unit tests passed, but the real Next production build rejected that import path.

Final implementation uses:
prerender from react-dom/static

The prelude stream is completely drained before the file is measured or returned.

A dedicated test compares the report produced through the normal renderer with Next's compiled
static Node React implementation.

A boundary rule now bans react-dom/server so the same production-only failure is caught earlier.

HOSTILE-CONTENT TESTING
Hostile report data is checked structurally with parse5.

The tests do not simply ban strings such as javascript:, data:, url( or <script>, because those
strings may legitimately appear as report evidence.

Instead the parsed document is checked for:
- forbidden elements
- event-handler attributes
- fetching/navigation attributes
- external CSS/resource references

Hostile payload text must remain visible as text rather than being silently deleted.

DANGEROUS INVISIBLE CHARACTERS
Dangerous invisible characters are displayed visibly in U+XXXX-style notation.

Covered classes include:
- unsafe C0 controls
- C1 controls
- bidi embeddings/overrides
- bidi isolates
- lone surrogate code units

TAB and LF are preserved.

CARRIAGE RETURN REVIEW FINDING
Independent review found that U+000D carriage return was initially left out of the unsafe C0 set.

HTML parsing normalises CR/CRLF line endings, so preserving raw CR could silently mutate observed
evidence.

Final behavior:
- TAB survives
- LF survives
- CR becomes visible U+000D notation
- CRLF becomes visible U+000D notation followed by the preserved LF

SURROGATE BUG FOUND DURING IMPLEMENTATION
An early lone-surrogate regex also matched part of valid surrogate pairs and mangled normal emoji.

It was replaced with a Unicode-aware surrogate-category match.

Regression tests preserve valid astral Unicode while still identifying genuinely unpaired
surrogates.

SEVERITY CAP REVIEW FINDINGS
First defect:
the renderer treated the presence of score.cap as proof the score had actually been limited.

That was false because an applicable severity cap can exist while the weighted score is already
below the cap ceiling.

Second defect:
the new shared rule used JavaScript Math.round.

ScanCompass's scoring methodology deliberately uses round-half-down:

- Math.round(-value)

Example:
pre-cap 74.5
cap ceiling 74
published score 74

Without the cap, round-half-down(74.5) is also 74.

Therefore the cap did not change the published score and must not be described as limiting it.

Final presentation code mirrors the product's round-half-down display semantics without importing
or changing the frozen scoring engine.

Tests include:
- 74.5 -> no cap explanation
- 74.500001 -> cap explanation
- ordinary non-half values
- unpublished score
- null final score
- null pre-cap score
- dense comparison from 1 to 100 in tenths, including every half
- scoring source still uses the mirrored rule

FILENAME / CONTENT-DISPOSITION SAFETY
Filename format:

scancompass-<safe-hostname>-<YYYY-MM-DD>.html

Hostname slug is built from:
[a-z0-9.-]

Header-breaking characters cannot be copied directly into the filename.

Hostile cases cover CR/LF, quotes, semicolons, backslashes, path-like input, controls,
non-ASCII text, emoji, bidi characters, empty names and very long names.

Malformed dates are omitted rather than converted into garbage punctuation.

Successful response includes:
Content-Type: text/html; charset=utf-8
Content-Disposition: attachment
Cache-Control: no-store, no-cache, must-revalidate
Referrer-Policy: no-referrer
X-Robots-Tag: noindex, nofollow
X-Content-Type-Options: nosniff
