RECIPIENT CONTRACT
Recipient handling is:

1. trim
2. validate as one email address
3. enforce MAX_RECIPIENT_LENGTH = 254
4. normalize with lowercase only

The request object is strict and accepts exactly:
- managementToken
- recipient

Rejected forms include:
- comma-separated lists
- semicolon-separated lists
- display-name forms
- CR/LF injection
- NUL
- quoted local parts
- localhost/no-dot domains
- address literals
- malformed domains
- extra object keys

Normalization deliberately does NOT:
- remove +tags
- remove dots
- rewrite domains

The same normalized string is:
- HMACed
- sent to the provider

This prevents the abuse identity from diverging from the actual delivery target.

RECIPIENT HMAC
Recipient identity is:

HMAC-SHA-256(
  normalizedRecipient,
  EMAIL_RECIPIENT_HMAC_KEY
)

The key is:
- dedicated to recipient identity
- base64 encoded
- required to decode to exactly 32 bytes
- not reused for management/share capabilities, sessions, signatures or encryption

The raw recipient address is not intentionally persisted.

The persistence schema stores recipient_hmac, not a plaintext recipient address/domain.

HMAC ROTATION DECISION
Step 12 uses the approved single-key v1 strategy.

hmac_key_id = v1

Rotation is unsupported until v1 delivery rows have aged out.

Reason:
anonymous rows are bounded by the existing 90-day maximum, so the wait is finite.

Recorded trade-off:
an emergency key rotation inside that window could allow the same address to be emailed once
again for one scan because the new digest would not match the old-key digest.

DELIVERY RESERVATION ORDER
The approved transaction order is:

1. lock scans row
2. re-read management capability under the lock
3. count shares
4. count deliveries
5. mint share and extend retention
6. INSERT report_deliveries as RESERVED
7. COMMIT
8. only then attempt provider delivery

No provider call occurs while the transaction is open.

The unique:
(scan_id, recipient_hmac)

constraint remains the final duplicate-race backstop.

CAPS
Total shares per scan:
5

Total email delivery rows per scan:
3

Same recipient per scan:
1 row

Every delivery row counts regardless of status.

Therefore:
- FAILED does not free a slot
- UNKNOWN does not free a slot
- revocation does not create another recipient attempt
- a retry for the same recipient does not create another provider call

AT-MOST-ONE PROVIDER ATTEMPT
Step 12 deliberately treats at-most-one-provider-attempt as an abuse/privacy rule.

After:
- definite failure
- ambiguous outcome
- lost response

the same recipient is not automatically mailed again for the same scan.

A same-recipient retry returns the already-requested result and performs zero additional provider
calls.

This avoids duplicate mail to a recipient when the provider outcome cannot be established safely.

DELIVERY STATUS MODEL
Stored statuses:

RESERVED
SENT
FAILED
UNKNOWN

Meaning:
- RESERVED: durable reservation exists, provider outcome not yet recorded
- SENT: provider positively accepted the message
- FAILED: provider definitely refused / definitely could not be reached in a non-ambiguous way
- UNKNOWN: the provider may have received the request, but the final outcome cannot be established

A process crash after reservation but before provider I/O can leave RESERVED.

No recovery worker was added in Step 12.

COMMIT AMBIGUITY
If the database COMMIT is sent but acknowledgement is lost:

- the provider is NOT called
- no email token is sent
- response is service-unavailable class
- an inert share/delivery row may have committed and consumed a slot

No automated recovery path was added.

A later same-recipient retry is:
- refused if the row exists
- permitted if the row did not commit

This avoids guessing the transaction outcome.

PROVIDER OUTCOME MODEL
Provider result vocabulary:

ACCEPTED
DEFINITE_FAILURE
OUTCOME_UNKNOWN

Examples of definite failure:
- bounded valid provider refusal
- provider 4xx
- connection refused before request delivery
- TLS failure before request delivery

Examples of ambiguous outcome:
- timeout/reset after the request may have been written
- malformed/oversized response
- provider 5xx

Ambiguous outcomes are never automatically retried.

API RESPONSE SEMANTICS
Important response classes include:

- invalid request / recipient -> 400
- management-capability refusal -> neutral 404
- email disabled/unavailable -> 503
- DB unavailable -> 503
- commit outcome unknown -> 503
- provider outcome unknown -> 503-class
- five-share cap -> existing SHARE_LIMIT_REACHED 409
- three-delivery cap -> DELIVERY_LIMIT_REACHED 409
- same recipient already attempted -> DELIVERY_ALREADY_REQUESTED 409

The two new 409 codes are authenticated-only and are added centrally rather than hand-built in
the route.

Responses preserve:
- no-store
- no-referrer
- noindex posture

BROWSER REVOCATION METADATA
Successful email creation returns:

{
  ok: true,
  shareId,
  expiresAt
}

It never returns shareToken.

The browser records the resulting share metadata as an emailed link that is not locally copyable.

The raw share URL cannot be recovered from the server later because only the digest is stored.

On provider FAILED or UNKNOWN:
- shareId is still returned
- the owner can revoke a link that may have been delivered

The server does not auto-revoke an UNKNOWN delivery, because the email may in fact have arrived.

TIMEOUT RECONCILIATION
The original design review described a 5-second connect timeout and 10-second total timeout.

Implementation review established:
- fetch has no connection-phase hook
- undici Agent connect timeout was unavailable because undici was not resolvable as a project dependency
- node:https could implement connect-only timing, but is banned by the raw-network boundary and
  weakening that boundary was not approved

The final enforced contract is:

PROVIDER_HEADERS_TIMEOUT_MS = 5,000 ms
covering:
- DNS
- TCP
- TLS
- request write
- response headers

PROVIDER_TOTAL_TIMEOUT_MS = 10,000 ms
covering:
- the complete exchange
- response-body drain

MAX_PROVIDER_RESPONSE_BYTES = 64 KiB

This is stricter than a connect-only timeout because a provider that connects but stalls before
headers is also bounded.

The implementation empirically verified that fetch resolves when response headers arrive before
the body finishes, so the early and total bounds can be armed independently.

A dedicated regression test proves clearing the headers timer does not disarm the total timer.

The documentation was corrected to describe the actual behaviour honestly rather than continuing
to call the 5-second bound a connect-only timeout.

IMPLEMENTATION DEFECTS FOUND AND CORRECTED
Four important defects/design problems were found during implementation:

1. UNIQUE-VIOLATION TRANSACTION HANDLING
An early version tried to catch a PostgreSQL unique violation and continue inside the transaction.

Problem:
a statement error aborts the PostgreSQL transaction, so continuing to COMMIT could not work
correctly.

Correction:
duplicate pre-check occurs under the scan lock; the unique index remains the final race backstop.

2. SERVER-ONLY IMPORT GRAPH
The first request-schema composition pulled a notify/server-only module into a transport import
graph that could become jsdom-reachable.

Correction:
the cross-dependency was removed instead of weakening the server-only guard.

3. VENDOR CONFINEMENT
An intermediate config module hard-coded Postmark-specific details outside the provider area.

Correction:
the provider registry/adapter owns the vendor mapping.

4. UNUSED DIGEST COMPARISON
An unused timingSafeEqual-based digest helper widened a security-rule allowlist without serving
runtime behaviour.

Correction:
the dead helper was removed rather than exempted.
