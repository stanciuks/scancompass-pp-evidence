PERSISTABILITY RULE
Application rule, evaluated before opening a transaction:

COMPLETED        -> persist
PARTIAL          -> persist
DEADLINE_REACHED -> do not persist
CANCELLED        -> do not persist
FAILED           -> do not persist

The PostgreSQL CHECK constraint is a backstop, not the primary decision-maker.

TRI-STATE DURABILITY
Public response durability:

persisted: true
- COMMIT positively acknowledged
- scanId returned

persisted: false
- definitely not committed, or no transaction attempted
- no scanId

persisted: null
- COMMIT was sent but the outcome cannot be established
- no public scanId

Core invariant:
A response with persisted:false cannot later correspond to a committed
transaction.

COMMIT AMBIGUITY
Explicit phase tracking:
NO_TRANSACTION
-> TRANSACTION_OPEN
-> COMMIT_SENT
-> COMMIT_ACKNOWLEDGED

Before COMMIT:
failure or expiry gives definite NOT_PERSISTED.

After COMMIT has been sent:
a connection loss / timeout / unacknowledged result is classified as
UNKNOWN / COMMIT_OUTCOME_UNKNOWN, not false.

The candidate scanId is retained only for safe internal logging and never becomes
a public scanId or management capability.

DEADLINE / CLIENT LIFECYCLE
A targeted pre-commit lifecycle audit verified:
- deadline timer is disposed on every completed attempt
- a timer cannot destroy a client after PERSISTED has returned
- client release/destroy is idempotent and occurs at most once
- late acquisition after timeout is destroyed and never starts BEGIN
- successful COMMIT cannot later turn into timeout behaviour
- no deadline callback mutates breaker state
- no abandoned promise produces an unhandled rejection
- candidateScanId is internal/log-only

The audit required no source change.

POOL ACQUISITION SAFETY
A real Step 7 gap was found during fault-injection testing:

persistAssessment originally awaited acquire() without its own wall-clock bound,
relying on pg's connectionTimeoutMillis.

It was corrected so acquisition races the writer's own deadline.

A late-resolving acquisition is immediately destroyed/released and never begins
a transaction.

CIRCUIT BREAKER
Process-local state machine:
CLOSED
OPEN
HALF_OPEN

Open duration:
30,000 ms

Behaviour:
- DB runtime failure -> OPEN
- OPEN before cooldown -> skip immediately
- after cooldown exactly one caller becomes HALF_OPEN
- concurrent callers skip
- successful probe -> CLOSED
- failed/unknown probe -> OPEN again

Breaker opens on:
- DATABASE_ERROR
- WRITE_TIMEOUT
- COMMIT_OUTCOME_UNKNOWN

Breaker does not open on:
- NOT_CONFIGURED
- CONFIG_INVALID
- STATE_NOT_PERSISTABLE
- ARTIFACT_INVALID
- ARTIFACT_TOO_LARGE
- INTERNAL_ERROR

No timer job, polling loop, or background DB health task is used.

   the schema.

   without changing public report bytes.
3. A replacement determinism assertion was itself timing-dependent and was replaced
   with deterministic non-vacuity checks.
4. Several new boundary rules were initially too broad because they matched
   "persistence" by substring. They were narrowed to structural/import semantics.
5. An import cycle appeared when durability vocabulary lived in admission.ts.
   Resolved with neutral launch/durability.ts.
6. Pool acquisition was initially unbounded by the writer's own deadline. This was
   found by fault-injection tests and corrected.
7. The first fake pg connection did not reject an in-flight query when destroyed,
   unlike the real driver behaviour. The fake was corrected rather than weakening
   the assertion.
8. Two structural rules incorrectly treated legitimate existing repository concepts
   as forbidden globally (copyParams and declarative management-token schema
   references). They were scoped to executable Step 7 writer behaviour instead.
