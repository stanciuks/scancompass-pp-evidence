2. THE OLD, PLANNER-DEPENDENT STATEMENT

Both batch operations were ONE statement:

  DELETE FROM scans
   WHERE id IN (SELECT id FROM scans
                 WHERE <predicate>
                 ORDER BY <order>
                 LIMIT n
                   FOR UPDATE [SKIP LOCKED])

The limit bounds each EXECUTION OF THE SUB-SELECT, not the delete. Under a
nested-loop plan the sub-select is re-executed per outer row, the row-locking
step skips tuples this statement has already deleted, and the limit therefore
yields the next n SURVIVING candidates each time — so the statement can delete
far more than n. The mechanism and its statistics trigger are in the diagnosis
note.

AN AUDIT OF EVERY STATEMENT AND CALLER IN THE RETENTION MODULE established that
these TWO SHAPES ARE THE ONLY AFFECTED STATEMENTS. The other ten
select-for-update sites in the codebase are all top-level, awaited selects
inside a transaction, none embedded in a data-modifying statement; and the only
other variable limit is a read with no lock and no delete.

4. THE CORRECTED SHAPE

Each batch is now ONE TRANSACTION OF TWO QUERY-BUILDER STATEMENTS:

  BEGIN
  SELECT candidate ids
    WHERE <predicate> ORDER BY <order> LIMIT n FOR UPDATE [SKIP LOCKED]
      -> materialised as a concrete list in application memory, length <= n
  DELETE WHERE id IN (<those exact ids>) AND <the same predicate>
      -- sent only when the list is non-empty
  COMMIT

  - the candidate select is a TOP-LEVEL statement, so its limit is FINAL.
    Nothing re-executable reaches the delete, which names a parameter list and
    therefore cannot affect more than the selected rows under ANY PLAN;
  - THE EXPIRY SWEEP KEEPS ITS NON-BLOCKING LOCK so concurrent sweeps divide
    the work, and THE DENYLIST PURGE KEEPS ITS BLOCKING LOCK so it waits rather
    than silently skipping. Both are pinned by unit tests for every scope;
  - CANDIDATE SELECTION AND DELETION HAPPEN IN THE SAME TRANSACTION, so the row
    locks taken by the select are held until the commit;
  - AT MOST BATCH-SIZE IDS ENTER THE DELETE, asserted on every recorded
    statement;
  - AN EMPTY SELECTION ISSUES NO DELETE AT ALL and returns zero;
  - THE DELETE REPEATS THE PREDICATE. Under the held locks that is redundant —
    which is the point: if the locking reasoning were ever wrong, a row that
    stopped matching would be LEFT ALONE rather than deleted;
  - INVARIANT CHECKS THAT FAIL CLOSED. More ids than the limit, a repeated id,
    or a delete row count that disagrees with the number of locked candidates
    (or is missing) raises a dedicated error carrying NO IDS, HOSTNAMES OR
    COUNTS. Throwing inside the transaction ROLLS IT BACK, and the orchestrator
    reports the run as incomplete with the batch UNCOUNTED. A short count would
    be the worst outcome, because the sweep reads a short batch as "done for
    now" and the purge reads zero as "completed";
  - NO RAW SQL. The query builder is used throughout. A materialised common
    table expression would also stop the re-execution, but only as raw SQL, and
    the transaction gives the code a candidate list it can COUNT AND CHECK;
  - the public interfaces, the batch size of 200, the limit of 10 batches per
    run, the result types and the operator command are unchanged. The
    application role keeps exactly the privileges it already had. NO SCHEMA,
    MIGRATION OR GRANT CHANGE.

THE TWO EXISTING TESTS THAT CAUGHT THE DEFECT ARE UNCHANGED. No test was
skipped, deleted or weakened.

5. TESTS

TWENTY-TWO new PostgreSQL tests, ALL RUN UNDER THE FORCED RESCANNING PLAN, plus
35 unit tests on the statement shapes.

Covered: the two permanent reproductions; an empty batch for all three
operations, proving NO DELETE IS SENT; exactly batch-size; batch size one over
three rows; multiple batches ending in a partial one; the id count entering
every recorded delete; and decoy rows just outside each predicate — one
millisecond past expiry, a far-future row, a similarly-named host and a
look-alike subdomain — all SURVIVING, which is what proves the scope was never
the problem.

REAL CONCURRENCY PROOFS, with waits OBSERVED in the database's activity view
rather than assumed:

  - TWO EXPIRY WORKERS DIVIDE THE WORK: worker 1 is held after locking two ids,
    worker 2 is NOT BLOCKED and takes the next two, the held ids are still
    present while held, and worker 1 then deletes exactly its two;
  - THE PURGE WAITS AND NEVER SKIPS: a second batch is observed waiting on a
    lock, and after release each batch deletes its own rows;
  - A TIMEOUT ROLLS BACK: a batch cancelled by the statement timeout reports
    incomplete with zero deleted, sends no delete, issues a rollback — AND THE
    SAME CONNECTION THEN COMPLETES A NORMAL BATCH, so the connection remains
    usable;
  - a delete count disagreeing with the locked candidates fails closed, the
    genuine candidate is STILL PRESENT because the transaction rolled back, and
    the next run is normal;
  - a candidate list longer than the limit is refused BEFORE ANY DELETE;
  - an empty selection claims no more than the old statement's snapshot did.

Results: the retention suite 45 PASSED (23 existing plus 22 new), repeated
20 TIMES, 20 OF 20 PASSED, then 5 more after a refinement to the statistics
setup, 5 of 5.

8. REMAINING ISSUES

  - the statistics state that triggers the bad plan can still occur in the test
    database. With the fix it no longer matters, because the bound no longer
    depends on the plan — and the new block forces that plan on every run;
  - a batch now holds its row locks across two statements rather than one, so a
    competing operation can wait up to two statement bounds instead of one. In
    practice milliseconds;
  - the new invariant error is reported under the existing coarse failure
    reason rather than a new one, deliberately, to keep the public taxonomy
    unchanged. An operator sees "rerun", and the rerun is safe because the
    failed batch rolled back;
  - PRODUCTION RETENTION HAS NEVER RUN AGAINST A POPULATED DATABASE WITH THIS
    CODE. The bound and its locking are proven on disposable PostgreSQL 18.6
    only;
  - the diagnostic's raw logs are not kept in any repository; this work
    re-derives the mechanism independently;
  - the residual items carried from PR #20 are unchanged.
