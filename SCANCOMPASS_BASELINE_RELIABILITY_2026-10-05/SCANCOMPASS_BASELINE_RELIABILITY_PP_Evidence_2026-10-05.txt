2. WHY THIS EXISTS

Four defects in the repository's TESTS AND ACCEPTANCE TOOLING — not in the
product — had been independently reproduced during the payment-after-domain
rehearsal. Each was reproduced AGAIN here on untouched main before anything was

On untouched main the full suite showed 4 failed of 7,102, and the acceptance

3. DEFECT 1 — THE ACCEPTANCE RUNNER REFUSED A GENUINE POSTGRESQL 18.6

The runner reported that the disposable server was not PostgreSQL 18.6. The
image IS PostgreSQL 18.6, so the verdict was FALSE — and the runner did not log
the version query's output, so the cause had to be established separately.

3.1 THE REPRODUCTION: 18 OF 20

The runner's readiness sequence was replayed command for command against 20
fresh containers:

  the version query succeeded                              2
  "database ... does not exist"                            9
  "the database system is shutting down"                   5
  "connection to server on socket ... failed"              4

18 OF 20 WOULD HAVE REFUSED. On this host the runner was effectively unusable.
The rate is specific to the host — the readiness step had not tripped during
the original executions on a different machine — and the record says so: the
number is evidence that the race is REAL, not a measure of how often it occurs
elsewhere.

3.2 THE ROOT CAUSE

The image's entrypoint initialises a new cluster by starting a TEMPORARY server
bound to a Unix socket only, creating the database, stopping it, and only then
starting the real server on TCP. A traced container log shows all of it: the
temporary server accepting connections, a probe failing because the database
did not exist yet, the fast-shutdown request, a probe refused during shutdown,
and finally the real server listening on TCP.

The readiness tool reports "accepting connections" from the TEMPORARY server —
and does not check that the named database exists — so the gate opened on a
server that was about to disappear. The single version query that followed
landed in one of three windows and failed to connect, and the runner treated
ANY failure of that query as a VERSION FACT.

TWO DEFECTS COMPOUNDED: readiness was proven against the wrong server, and a
connection failure was reported as a version.

3.3 THE CORRECTION: A READINESS PROOF, NOT A READINESS GUESS

  - FINAL SERVER ONLY. Each probe connects over TCP to the loopback address,
    and the ANSWER ITSELF must report that it came from that address. The
    temporary server listens on no TCP address, so it cannot answer at all;
  - STABLE. Three consecutive successful probes 250 ms apart FROM THE SAME
    POSTMASTER, identified by its start time. A failure, or a different start
    time, resets the count;
  - EXACT VERSION FROM TWO SOURCES, which must both parse and agree, and must
    be exactly 18.6. This is STRICTER than before: the old substring test would
    have accepted "PostgreSQL 18.60";
  - FAIL-CLOSED. A well-formed wrong version refuses IMMEDIATELY and is never
    waited out. An unparseable or self-contradictory answer gets its own new
    refusal code, also immediate. A connection failure is only "not yet" — and
    still "not yet" at the deadline becomes a third, distinct refusal carrying
    the last failure text, so the runner can no longer report a connection
    problem as a version problem;
  - BOUNDED. A 60-second deadline on an INJECTED clock, plus a probe cap so a
    clock that does not advance still terminates, plus a per-probe timeout so
    one hung command cannot hold the loop. The only sleep is the 250 ms
    interval; there is no fixed "wait for init" sleep;
  - supervision, cancellation and cleanup are unchanged, and the check's
    displayed name is unchanged.

4. DEFECT 2 — TWO TESTS READ THE REAL CLOCK AGAINST A PINNED FIXTURE

Two signup tests built a challenge expiring 60 seconds after a PINNED instant
but passed only the hasher, not the clock, into a service that already takes a
clock seam. They therefore compared a fixed fixture against the real clock, and
FAILED FROM ONE MINUTE PAST THAT INSTANT ONWARDS — every other completion test
in the file already passed the clock.

Confirmed by running main's unmodified file with the process clock shifted one
year BACK: 17 of 17 pass; unshifted, 2 fail. The dependence is on wall time and
nothing else.

The fix is two lines — pass the clock — but the REGRESSION WORK is the
substance: 30 new boundary tests covering one millisecond before expiry,
exactly at expiry and one millisecond after, for the hashed, rejected-password
and busy-hasher paths, each asserting what ran, what did not, and what was
deleted. EACH CASE RUNS AT THREE ANCHORS: the fixture's own date, the year
2000 and the year 2100. A test that fell back to the real clock CANNOT pass at
both the 2000 and the 2100 anchor, so the suite now fails TODAY on such a
regression instead of on some future date.

MUTATION CHECK: replacing the injected clock with nothing in the boundary tests
produced 12 failures — exactly the cases whose verdict the real clock
contradicts. A separate audit, not committed, shifted the clock forward by one
day, 31 days and 365 days across 18 account and API test files, 482 tests, all
passing.

5. DEFECT 3 — A NETWORK DEPENDENCY IN THE TEST PATH

A policy-regeneration test shelled out to a TypeScript runner that is NOT a
dependency of this repository, so the package runner fetched it from the
registry at test time. Here it printed notices and then failed outright, and in
a network-restricted environment it CANNOT work at all.

Plain Node could not replace it: the generator's import graph uses
extensionless relative imports, which Node's type stripping does not resolve.
That was verified rather than assumed, and REJECTED as a fix because making the
graph resolvable would mean rewriting imports in PRODUCTION SOURCE — out of
scope for a test-reliability change.

The test now imports the generator through the test runner's OWN TypeScript
loader, which is a declared, installed dependency. Importing runs the module
exactly as its command line does, and the test asserts the output file is
byte-identical before and after and equal to the module's own rendering. NO
DEPENDENCY WAS ADDED. Drift detection was verified by appending a line to the
committed file and watching the test fail.

6. DEFECT 4 — A TEST TIMEOUT WITH A MEASURED CAUSE

Not a hang and not a network problem. Each start of the retention command costs
a near-constant 0.63 to 0.68 seconds, MEASURED 12 TIMES on an idle host and
dominated by loading its import graph. The failing test spawned EIGHT of them
sequentially inside ONE test with a 5-second budget: about 5.1 seconds even
idle, and under full-suite load a single spawn was measured at up to 1.47
seconds, so the test needed 8 to 12. Every other test in the file spawns at
most two.

The eight-case loop became eight separate tests, each with its own 5-second
budget — roughly seven times headroom idle and three times at the worst
measured loaded spawn. EVERY CASE AND ASSERTION IS KEPT, AND THE TIMEOUT WAS
NOT RAISED. Measured afterwards: 620 to 685 milliseconds each.
