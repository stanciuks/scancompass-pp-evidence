2. THE OBSERVATION THAT STARTED IT

PR #19 ran the acceptance runner ten times. Run 7 failed on one assertion:

  concurrent wrong passwords lose no increment
  AssertionError: expected 5 to be 6

The test fires six wrong-password logins concurrently against one account and
expects the durable failure counter to read 6. SIX REAL FAILURES WERE MADE;
FIVE WERE DURABLE.

3. SOURCE DIAGNOSIS

The login route captured the current time BEFORE the password-verification
step, and that single instant was then used for every time-based decision that
followed. Password verification is deliberately slow and
concurrency-limited, so the gap between capturing the instant and committing
the failure is both large and VARIABLE.

The row lock serialises the read-modify-write correctly. WHAT A LOCK CANNOT DO
IS MAKE THE INSTANTS ARRIVE IN COMMIT ORDER: each attempt's instant was fixed
before its hashing step, and hashing-completion order and lock-queue order are
independent of start order.

The losing interleaving, exactly:

  1. attempt A starts at t1 and is slow in the hashing step;
  2. attempt B starts at t2, later than t1, finishes hashing first, takes the
     row, and commits a count of 1 with its observation window opened at t2;
  3. A then takes the row and computes an elapsed time of t1 minus t2, which is
     NEGATIVE. The policy's window check requires a non-negative elapsed value —
     its own comment says a window start in the future is clock skew — so it
     reports no active window, and A writes a count of 1 with a window opened
     at t1.

B's increment is erased. With several concurrent attempts, every out-of-order
commit resets the count, which is why observed values ranged from 1 to 5 out of
6. AN ATTACKER SENDING WRONG PASSWORDS CONCURRENTLY COULD KEEP THE COUNTER FROM
EVER REACHING THE THRESHOLD. That is a durable-lockout weakness, not a test
artefact.

EVERY OTHER CONSUMER OF THAT STALE INSTANT WAS AUDITED, not just the one that
failed. Five more were found: the successful-login lock re-check (wrong, though
in the conservative direction), the account's updated timestamp, a credential
rotation timestamp recorded before the rotation happened, and a session row
whose creation, last-used and expiry timestamps all predated its own creation
by the hashing and lock-wait time. Separately audited and found CLEAN: the
reset and signup flows, which already read their clock after their locks;
session resolution, whose guarded update cannot move its timestamp backwards;
and three store functions that stamp a column without making a time-based
decision.

starts with the earlier instant and is held at a gate inside its real hashing
step; attempt B starts 40 milliseconds later, completes hashing and queues on

database's activity view rather than assumed; the holder rolls back and the
database grants B, then A. Result every time: expected 2, observed 1.

5. THE CORRECTION

The pattern already established elsewhere in this project: HAND OVER A CLOCK,
AND READ IT WHERE THE DECISION IS MADE.

  - the lockout store function now OWNS a clock function and calls it ONCE,
    AFTER its select-for-update returns. The instant goes to the transition and
    to the updated timestamp. BECAUSE THE STORE OWNS THE READ, NO CALLER CAN
    SUPPLY A STALE INSTANT;
  - successful-login finalisation likewise reads ONE fresh instant after the
    account row lock, and that instant decides whether the account is still
    locked and stamps the account, any credential rotation, and the session's
    creation, last-used and expiry times;
  - the login input's time field was REMOVED from the type; the clock is a
    default-real dependency instead;
  - the route supplies NO TIME AT ALL, so production always uses the real clock
    and no body, query or header can reach it;
  - the database's own transaction-start time function was DELIBERATELY NOT
    USED: it is fixed before the lock wait and would be stale in exactly the
    same way.

WHY THE INSTANT IS NOW ORDERED: transaction k reads the clock after acquiring
the row lock, which it acquires only after transaction k-1 commits, which
happens after k-1's clock read. On one host the instants are therefore
non-decreasing, so a committed window start is never in the future for the next
transition.

PRESERVED UNCHANGED: the threshold of 10, the 15-minute observation window, the
15-minute lock duration, the rule that a failure during an active lock neither
extends it nor counts, lock release at its expiry, the clearing of the lockout
state on a successful login or a reset, the dummy key-derivation run for
unknown, disabled, deleted, unverified, credential-less and
unsupported-verifier accounts so that none of them is distinguishable by
timing, the behaviour that a busy hasher records nothing, the hashing
concurrency limiter, session rotation, the credential-fingerprint re-check, and
the single public refusal.

THE CLOCK-SKEW GUARD WAS KEPT, NOT DELETED. The non-negative-elapsed check and
its unit test remain. It is now reachable only by a genuine backwards step of
the host clock, not by ordinary concurrency, and that residual is recorded in
section 8 rather than papered over.

6. TESTS

THIRTEEN NEW POSTGRESQL CONCURRENCY TESTS were added as their own section.
Their scheduling is deterministic: an administrative blocker holds the account
row, and the test WAITS UNTIL THE DATABASE'S OWN ACTIVITY VIEW SHOWS the
expected number of this file's transactions queued on that row, with at least
one blocked directly by the blocker, before releasing. Gates hold the real
hashing step. Clocks are injected so the instant each transition used can be
asserted. NO SLEEP DECIDES AN ORDERING.

They cover: a later-started failure that commits first not erasing an
earlier-started one, with the clock reads asserted to have happened under the
lock and in commit order; eight failures queued on one row lock all counting;
nine unsynchronised attempts against the real clock losing no increment;
crossing the threshold concurrently creating EXACTLY ONE lock, timed from the
tenth under-lock instant; a failure inside an active lock not extending it; the
lock-expiry boundary at minus one millisecond, exactly, and plus one
millisecond; the failure instant being read after a slow hashing step; an
unknown address running the dummy hasher and leaving EVERY ACCOUNT ROW
BYTE-IDENTICAL; a busy hasher writing nothing; a password reset landing during
a wrong-password attempt not restoring the stale count; a reset during a
correct-password login not restoring the old credential through rehashing; the
session being stamped from the post-lock instant; and a lock set during a
correct-password attempt refusing it.

Six other test files were adjusted to the new clock seam, including one new
route assertion proving that the route passes exactly the intended fields and
no time, despite query parameters, a 1970 date header and a header named for
the clock — and that a request body carrying a time is rejected before it ever
reaches login. NO TEST WAS SKIPPED, DELETED OR WEAKENED, and the runner, its
manifest and its phase inventory are untouched.

Results on the fixed code: the account-session suite 58 passed; the lockout
sections repeated 20 TIMES, 20 PASSED, 0 FAILED.

A GATE FAILURE WAS HIT AND FIXED BEFORE COMMIT, and the direction of the fix is
the point: a boundary test pins the login module as the only place that decides
session expiry. The first draft passed that policy function to the store. THE
RULE WAS KEPT AND THE CODE CHANGED — the login module now passes a closure, so
the policy is still decided in one place and the store supplies only the
instant.

8. REMAINING ISSUES

  - the retention failure above — open at the time, since diagnosed and fixed;
  - BACKWARDS HOST-CLOCK STEPS. With the instant read under the lock, a failure
    can still precede a committed window start only if the host clock itself
    steps backwards. The existing policy then restarts the count once; it
    cannot create or extend a lock. A clamp would close it but changes lockout
    semantics, so it is left for a reviewed decision. The deployment is a single
    host, which bounds this;
  - a failure verified against a credential that a reset superseded mid-attempt
    still counts once. It cannot restore the pre-reset count. Not counting it
    would need the credential fingerprint inside the failure transaction;
  - operator-facing script comments and a readiness caveat carried from PR #19.
