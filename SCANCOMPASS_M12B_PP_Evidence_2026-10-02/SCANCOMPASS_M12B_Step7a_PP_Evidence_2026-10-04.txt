2. THE GAP THIS CLOSES

M12B-7A needs ONE controlled operator account while public signup stays
closed, and at the parent commit the source offered no way to obtain one.

  Writer of account_signup_challenges — requestSignupChallenge — is reachable
  only through POST /api/account/signup, whose FIRST statement is the signup
  gate.

  Writer of account_email_challenges — the password-reset path — requires an
  account that does not exist yet.

  Writer of accounts and the initial credential — completeSignup, reached
  through POST /api/account/verify — is deliberately NOT gated, but it consumes
  a challenge that cannot be created.

So the completion half already worked. What was missing was any way to produce
the challenge it consumes. The gate is a PUBLIC-REGISTRATION control, and an
operator with shell access to the host and the application role's credentials
is not the party it exists to stop — but nothing in the source expressed that
distinction, so no path existed at all. [S3,S4]

3. REJECTED ALTERNATIVES

  Temporarily set ACCOUNT_SIGNUP_ENABLED=1 — opens registration to the entire
  internet for as long as an operator's attention lasts, with unbounded
  exposure and no artifact saying it happened.

  Hand-write accounts and account_credentials rows in SQL — requires producing
  an Argon2id digest by hand in the project's exact parameter string plus a
  state value, a verification timestamp and a credential row the login service
  will accept. Every one of those is a place to be silently wrong, and a wrong
  row looks exactly like a right one until a login fails.

  Generate a challenge token and INSERT it directly — duplicates the token
  minter, the digest, the TTL and the cap, all free to drift from the product.

  A new HTTP route behind a header, IP allowlist or one-time secret — a second
  permanently deployed public attack surface, with its own origin check, rate
  limit, client identity and audit story, for something done once.

  A new table, migration or grant — migration 0002 is applied in production
  and nothing about issuing one challenge needs new storage.

  A new container image — unnecessary; the existing maintenance image already
  contains the scripts and source tree. [S4]

5. DESIGN OF THE CLI

scripts/account-invite.ts is a one-shot operator command, not a route. It
mirrors the signup route's order with the public gate removed and nothing else
changed:

  1. account-email delivery availability   — config only; unavailable => exit 2
  2. application database availability      — config only; unavailable => exit 3
  3. read ONE address from stdin
  4. canonicalise it with the real parser
  5. requestSignupChallenge(db, {entered, canonical, now})  <- TWO arguments
  6. CREATED => send; a DEFINITE provider failure => discard the challenge
  7. print "operator invite request completed"

Step 5 passes TWO arguments, never three. The third parameter is the service's
dependency bag, and omitting it is what guarantees the service's own token
minter, digest, TTL, expiry sweep, per-address cap and per-address email lock
are used — so the CLI cannot become a second challenge generator. A test
asserts the argument count so this cannot regress.

The CLI creates no account, no credential and no password. The operator still
completes signup in a browser through the production verify route, proving
mailbox control and choosing a password under the real policy. [S4]

Both availability checks precede reading an address. At the route that ordering
is the enumeration defence; here it additionally means an operator learns that
mail is switched off BEFORE typing anything, rather than after a challenge row
exists that nobody can receive.

6. DISCLOSURE PROPERTIES

  - the address arrives on stdin, never in command-line arguments, so it
    reaches neither shell history nor the process table;
  - at a terminal the prompt reads with echo suppressed and prints no
    placeholder, because a row of asterisks would disclose the length;
  - the three service outcomes — challenge created, account already exists,
    live-challenge cap reached — produce BYTE-IDENTICAL output, so the tool
    cannot answer whether an address already has an account;
  - non-zero exits are operational only: each is a function of configuration
    or of the SHAPE of the input, never of any address's state in the
    database;
  - nothing printed contains the address, the challenge secret, the challenge
    identifier, the verification link, a connection string or a provider key.

One divergence from the route is deliberate and stated rather than hidden: a
MALFORMED address is refused instead of being collapsed into "accepted". The
route collapses it because answering differently would tell an anonymous
caller which spellings the server finds plausible; here the caller typed the
address at their own terminal, so there is no enumeration oracle to protect,
and silently accepting a typo would leave the operator waiting for a message
that can never arrive. The refusal still never echoes what was typed. [S4]

containing no real values is committed. [S4]

8. TESTS

Real PostgreSQL 18.6, committed role/grant templates, real migrations, a
disposable scratch database, and ACCOUNT_SIGNUP_ENABLED DELETED throughout —
12 assertions, 12 passed:

  - a challenge is issued with the signup flag absent, which is the gap;
  - the connection is the application role, asked of the database rather than
    inferred, and that role is refused CREATE TABLE with SQLSTATE 42501;
  - with account mail off the command fails closed and creates nothing;
  - the row carries a 32-byte digest, an expiry exactly 3,600,000 ms after
    creation, a zero attempt count, the entered spelling preserved and the
    canonical form lower-cased;
  - the mailed capability is NOT recoverable from the stored row cast to text;
  - the live-challenge cap is exact at 3 across four runs, with ONE distinct
    answer and three outbound messages;
  - an address that already has an account produces no row, no outbound
    message and the same answer;
  - a DEFINITE provider refusal removes the row; an INDETERMINATE answer
    keeps it;
  - the capability parsed out of the RECORDED PROVIDER PAYLOAD completes a
    signup, creating exactly one account and consuming the challenge;
  - the same capability cannot be used twice.

The capability used for the completion proofs is read from the recorded
provider payload rather than from a return value, so the thing proven usable is
the link that would have gone to a mailbox. The single outbound boundary is
replaced: no DNS lookup, no socket, and no message to any address.

Hermetic suites: 31 of 31 and 6 of 6. These cover the disclosure properties
with the service injected, including that stdin is NEVER read when mail is

cancellation keys, a 4096-byte input bound, and nine source boundaries. The
resolver-hook suite includes a NEGATIVE CONTROL proving the same import fails
