SESSION TOKEN CONTRACT
- 32 random bytes from Node CSPRNG
- unpadded base64url
- 43-character canonical wire form
- SHA-256 over the RAW 32 token bytes
- 32-byte digest
- digest is the value intended for sessions.token_hash
- plaintext token is wrapped immediately in SecretValue
- secret label: session-token

The token format is not independently redefined. It reuses constants and canonical parsing from:
src/server/security/canonical-token.ts

parseSessionToken() delegates to parseCapabilityToken(), preserving:
- exact length
- base64url alphabet
- decoded length
- canonical round trip
- one neutral undefined result for all malformed values

ACTOR CONTRACT
Actor has exactly two shapes:

ANONYMOUS
{ kind: "ANONYMOUS" }

ACCOUNT
{ kind: "ACCOUNT", accountId: string }

Actor intentionally contains no:
- role
- permission
- tier
- subscription/entitlement
- domain
- email/profile
- scanId
- reportId
- management/share capability

An account session therefore provides identity, not authorization.

SESSION COOKIE
Name:
__Host-scancompass_session

Live cookie attributes:
- Path=/
- Secure
- HttpOnly
- SameSite=Lax

Live cookie deliberately has:
- no Domain
- no Max-Age
- no Expires

This makes it a non-persistent browser session cookie. Server-side session lifetime remains a later
decision.

Clear-cookie attributes:
- same cookie name
- Path=/
- Secure
- HttpOnly
- SameSite=Lax
- Max-Age=0
- no Domain

The deletion Max-Age is the explicit exception to the live-cookie non-persistence rule.

HEADER BEHAVIOR
The helper uses Headers.append() rather than Headers.set(), so unrelated Set-Cookie headers are not
silently overwritten.

SECRET MISUSE GUARD
setSessionCookie() requires SecretValue.kind == "session-token".

A wrong secret kind:
- is rejected before reveal()
- writes no Set-Cookie header
- throws only an internal programming error
- does not put the raw secret in the error message or stack
