LOGIN ENUMERATION / FAILURE CONTRACT
Public refusal:
"Those details did not match an account."

Internally distinct account-specific failures collapse to that one public result:
- unknown identifier
- wrong password
- disabled/deleted account
- locked account
- missing PASSWORD credential
- unsupported stored verifier

Unknown, disabled and locked identities execute the dummy current-profile Argon2 path rather than
returning immediately. KDF BUSY is also mapped uniformly for known and unknown identifiers.

CREDENTIAL-FRESHNESS RACE
Password verification happens outside the short final database transaction.

Before session creation the transaction re-checks:
- account still ACTIVE
- account still verified
- account still unlocked
- credential still corresponds to the verifier that was proven

The committed PostgreSQL acceptance includes deterministic credential replacement inside the
verification/finalisation window and proves that zero sessions are created from the old credential.

OPPORTUNISTIC REHASH
M12B-5 added rehashVerifiedPassword().

After a stored password has already matched:
- raw input bound / Unicode well-formedness still apply
- NFC still applies
- fresh 16-byte nonce
- current Argon2id profile
- same KDF limiter
- no new-password minimum/blocklist reapplication

This allows a legacy password that would be rejected if chosen today to authenticate and be upgraded.

SESSION CREATION
Successful login creates:
- new session UUID
- new opaque random token
- SHA-256 token digest only in PostgreSQL
- created_at
- last_used_at = created_at
- expires_at = created_at + 7 days

No plaintext session token, IP, User-Agent or device label is stored.

SESSION FIXATION / ROTATION
A successful login deletes only the valid session presented by that browser and inserts a new one.
Other independent sessions for the account remain valid.

LOGOUT
POST /api/session/logout:
- exact trusted Origin
- no cookie -> idempotent success
- valid session -> delete exactly that row, then clear cookie
- stale/rejected cookie -> clear cookie, same success
- DB failure while revocation is needed -> 503 and cookie retained so revocation can be retried

LOGOUT-ALL
POST /api/session/logout-all:
- exact trusted Origin
- valid ACCOUNT actor required
- deletes every session for that account, including current
- clears cookie after commit
- anonymous -> 401
- stale cookie -> 401 plus clear
- DB failure -> 503

GET /API/SESSION
Returns only:
{ authenticated: true | false }

No account id, email, session id, expiry, lockout state, tier or permissions.

No cookie:
authenticated=false without requiring DB availability.

Presented cookie with DB failure:
503, not a false signed-out state.

SIGNUP CHALLENGE TOKEN
Challenge id:
canonical lowercase UUID

Secret:
32 random bytes, 43-character unpadded base64url

Stored:
SHA-256 digest of raw token bytes

Authorization lookup is by challenge UUID, followed by hashing of the supplied token and
timingSafeEqual comparison against token_hash.

Review correction clarified:
the stored digest is not itself a bearer credential; disclosure of the digest does not reveal the
32-byte token and still leaves a 256-bit preimage problem.

SIGNUP REQUEST
POST /api/account/signup

Order:
1. signup gate
2. delivery availability
3. exact Origin
4. trusted client identity
5. IP/global auth traffic limit
6. bounded strict body
7. account email canonicalization
8. challenge issuance
9. delivery attempt if created
10. neutral response

Request contains email only; no password is accepted yet.

Challenge issuance:
- deletes expired rows for that canonical email
- creates nothing if an account already owns the identity
- counts live rows
- stops at cap 3
- otherwise mints a fresh challenge
- never rotates/deletes still-live links merely to make room
- never resends an old secret

SIGNUP REQUEST ENUMERATION RESISTANCE
With a delivery dependency available, these address-dependent outcomes are byte-identical publicly:
- new challenge delivered
- existing account
- challenge cap reached
- delivery failed after challenge creation

The route returns one 202 body and no Set-Cookie.
Delivery-failure cleanup deletes the just-created row when cleanup succeeds.
Provider timing remains a documented residual.

SIGNUP COMPLETION
POST /api/account/verify is a class-2 capability-authorized mutation.

No session is required.

Phase 1:
- parse challenge id/token
- read row by id
- enforce expiry
- constant-time digest comparison
- canonical wrong token counts an attempt

Only after challenge proof:
Phase 2:
- new-password policy
- Argon2id outside the DB transaction

Phase 3:
under per-email serialization and a short PostgreSQL transaction:
- lock/re-read challenge
- re-check expiry/token
- ensure identity still free
- insert ACTIVE verified account
- insert one PASSWORD credential
- delete all pending signup challenges for canonical email
- commit

Registration creates zero sessions and sets zero session cookies.

CONCURRENT COMPLETION
Multiple valid outstanding links may race.

Required result, covered by committed acceptance:
- exactly one account
- exactly one PASSWORD credential
- zero remaining signup challenges for the canonical email
- losing completion receives neutral refusal
