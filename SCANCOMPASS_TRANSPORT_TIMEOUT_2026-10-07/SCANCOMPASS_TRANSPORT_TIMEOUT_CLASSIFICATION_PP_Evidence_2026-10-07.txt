2. HOW THE DEFECT WAS FOUND

It was not found by review, by a user, or by the work that was actually being
done. It was found because a continuous-integration run on the REDESIGN pull
request — one that changes no server or scanner code at all — failed exactly
one test out of 8,005. The test asserted that an operation deadline is
end-to-end rather than per redirect hop, and it received the reason code
REQUEST_TIMEOUT where it expected OPERATION_TIMEOUT. [S2,S3]

M12E's minimal CI gate had itself merged to main at 05:45:44 UTC. The run that
failed started at 05:57:27 UTC — ABOUT TWELVE MINUTES LATER, and the first
time that gate had been applied to this branch. [S1,S4]

3. WHY IT WAS NOT DISMISSED AS A FLAKY TEST

Three reasons were written down before any code was touched:

  - the failing test and the whole scanner network layer were BYTE-IDENTICAL to
    main on that branch. The test had passed on main's own push CI and on every
    run of the preceding pull request. So it was a LATENT DEFECT IN SHARED
    CODE, not something the change under test had introduced;
  - the same test's elapsed-TIME assertion passed. The timing was correct and
    only the REASON CODE was wrong, which points at a classification race
    rather than at a slow machine;
  - a test that sometimes reports the wrong reason is reporting a real
    nondeterminism in the code. The fix is to make the code deterministic;
    retrying the run or relaxing the assertion would only hide it.

4. THE ROOT CAUSE

The scanner's fetch enforces ONE end-to-end operation budget across all
redirect hops. For each hop it computes the remaining budget and arms that
hop's request timer for whichever is smaller, the configured per-request
timeout or the remaining budget. When the remaining budget is the smaller one,
THAT HOP'S TIMER IS THE OPERATION DEADLINE.

When the timer expired, the transport returned the per-request reason code, and
the caller upgraded it to the operation reason code only if a FRESH clock
reading showed the whole budget had been spent.

Node arms a timer from the event loop's CACHED time, so a timer can fire
slightly before the clock has advanced by its full delay. A local probe —
arming a 50 ms timer after work in the same loop iteration — saw this in 8 OF
20 TRIALS, by up to 1 ms. When it happens, the re-check finds the budget
fractionally unspent and the operation deadline is reported as a per-request
timeout. [S2]

5. THE CORRECTION, AND EXACTLY WHAT IT DOES NOT CHANGE

Before the request is made, the code now records whether the clamped hop
deadline IS the operation deadline. Classification is then decided from that
CLAMP rather than from a clock reading taken afterwards.

  clamped hop timer expires      reported as the operation timeout, decided
                                 from the clamp
  the two are exactly equal      the operation timeout, because the operation
                                 deadline is reached at that same instant
  a genuine per-request timeout  still the per-request timeout, when the
                                 configured limit is shorter than the budget
  the clock re-check             KEPT, as a second path, so nothing previously
                                 classified as an operation timeout can become
                                 a per-request timeout

THIS CHANGES THE REASON CODE ONLY. Timeout durations, the deadline arithmetic,
the operation budget, the redirect and request counts, and network authority —
which addresses may be contacted, and under what connection policy — are ALL
UNCHANGED. The new value feeds only the classification decision, and the timer
value passed to the request is the same expression as before. [S2,S3]

6. PROVING IT, INCLUDING THE ATTEMPT THAT DID NOT WORK

DETERMINISTIC REGRESSION. For the duration of one fetch call, the global timer
function is wrapped so that EVERY timer fires 3 ms before its nominal delay,
while the clock stays real. That is exactly the early-firing timer seen in CI,
made deterministic. Against a silent socket with a 60 ms budget, so that the
clamped hop timer is the operation deadline:

  old implementation   FAILS WITH CI'S EXACT ASSERTION — expected
                       REQUEST_TIMEOUT to be OPERATION_TIMEOUT
  with the fix         returns the operation timeout

COUNTER-CASE. With a silent socket, a 5-second budget and a 50 ms per-request
limit — a hop limit shorter than the remaining budget — the result is STILL
the per-request timeout.

AN EARLIER ATTEMPT IS RECORDED RATHER THAN OMITTED. Making the clock lag
uniformly did NOT reproduce the bug, because the start time lagged by the same
amount and the difference cancelled. That approach was tried and rejected while
the test was being written.
