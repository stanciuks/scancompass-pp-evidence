5. RUNTIME CODE (SOURCE-RECORDED) [S2,S3]

The change is persistence only. Its substance:

  AUTHORISATION. The existing domain-ownership rule was factored into one
  module-private decision helper plus one canonicaliser, used by BOTH the
  existing public check — whose behaviour is unchanged, proven by its own tests
  passing UNMODIFIED — and one new in-transaction variant that reads under a
  shared lock, takes its clock AFTER the locking read, and answers only
  authorised or not authorised. A read failure propagates and the enclosing
  transaction rolls back as unknown rather than as a denial.

  A SECOND TOOLING DEFECT, REPRODUCED. The query builder emits the shared-lock
  clause naming a schema-qualified table, which PostgreSQL refuses because that
  clause must name an unqualified relation. The reader therefore aliases the
  table, which is exactly the SQL the design specifies.

  THE STORE. Reserve, fenced release, consumption and abandoned-run hygiene
  statements live on the existing payment store, behind its existing account
  lock, and are bound to each locked account through a module-private map rather
  than published on the interface the M13 callers hold. The M13 test doubles of
  that interface are therefore UNCHANGED.

  LOCK ORDER. The declared payment lock order gains an M14 sub-stage beside the
  M13 stage, so NO M13 TRANSITION CHANGES MEANING. An entitlement must be
  acquired before the authorisation lock, before any run write and before any
  artifact work; re-writing a row already held is exempt; a run row may be
  written only for a held entitlement; and M13 entitlement writes are refused
  once authorisation or run work has begun.

  THE OUTCOME RULE. Reserve and consume wrap their whole body: ANY exception
  becomes an explicit "outcome unknown" answer carrying a cause, because the
  database layer gives no commit phase to inspect. The cause distinguishes the
  code's own invariant violations, lock-order violations and input faults from
  ordinary database faults. It is used for logging only.

  HYGIENE AND MINIMISATION. The retention command gains a pass that closes
  lapsed runs, and the per-host purge gains a pass that erases the stored
  retrieval summary for a purged host. That pass uses the TWO-STATEMENT,
  SKIP-LOCKED form established by this project's own batch-bound fix of
  2026-10-05, so it NEVER WAITS ON A LOCK and a query plan cannot re-execute its
  limit. Completion requires both a zero-row batch and a non-locking read
  finding no candidate; otherwise it pauses, retries a bounded number of times,
  and reports that the rows are locked rather than claiming success.

7. THE P0 DEFECT, AND WHY THE FIRST HEAD WAS NOT MERGED

THE INDEPENDENT REVIEW. An independent owner-side review of head 7dc5484 was
recorded on PR #43 as comment 6108125086 on 2026-10-11 at 10:34:43 UTC. Its
verdict: the continuous-integration and PostgreSQL evidence were substantial,
but it found ONE RELEASE-BLOCKING INVARIANT VIOLATION plus several corrections,
and it said in terms: DO NOT MERGE PR #43 YET. [S1,S4]

THE DEFECT. The design's load-bearing guarantee is that an entitlement may not
move to consumed without the durable frozen report existing AT THAT SAME COMMIT.
The first implementation did not enforce it. The artifact writer received the
RAW TRANSACTION and could write anything; after it returned, the verification
re-read ONLY the scan row's metadata. The integration suite's own success writer
wrote a scan row and a capability row but NO FROZEN REPORT AND NO FINDINGS — and
the test then expected, and got, a consumed entitlement. As the review put it,
the code PROVED THE OPPOSITE of the invariant it was supposed to establish.
[S4]

This is a defect of the most expensive kind for this project, because the money
is already taken by the time consumption runs: the end state would be a
consumed entitlement with no report to show for it.

THE REVIEW REQUIRED A STRUCTURAL FIX, NOT A CHECK. It asked that the write be
made structurally incapable of committing an incomplete artifact — a
store-owned, restricted write primitive reusing the existing pure row builders
in preference to an arbitrary raw-transaction callback — that the whole artifact
be verified before consumption, that NEGATIVE real-PostgreSQL tests be added for
each missing piece, that the happy-path fixture be changed to actually write the
report it claimed to test, and that no callback be allowed to become a bypass
around the declared lock order. [S4]

THE CORRECTION, ON THE SAME PULL REQUEST, AT HEAD a3c602c. The callback was
REMOVED. Consumption now takes the paid artifact AS ROWS, built before the
transaction opens by a new module that calls the existing M11 builders, so the
store owns every statement. It refuses a foreign or incomplete artifact BEFORE
ANY LOCK IS TAKEN. It then inserts the scan row, every findings chunk, the
frozen report and the initial capability WITH EACH STATEMENT'S ROW COUNT
CHECKED, and before it may consume it RE-READS THE WHOLE ARTIFACT THROUGH THE
COMPLETED RUN: the scan facts, exactly one report whose stored document
PostgreSQL ITSELF RE-HASHES to the expected digest and size, and exactly one
live capability with the expected digest. Anything else is a defect and the
whole transaction rolls back. NO GRANT WAS ADDED to make this possible. [S2]

PROVEN BY INJECTED FAULTS, NOT BY ASSERTION. Seven faults were injected into a
real PostgreSQL 18.6 database using database-level triggers created by the
administrative connection and scoped to the one scan under test: a missing
report row; a missing capability row; one missing finding; the report re-pointed
at another scan; and three that ONLY THE PRE-CONSUMPTION RE-READ CATCHES — a
document corrupted after insert, a capability revoked after insert, and a second
capability. EACH ONE ROLLED BACK AND NEVER REACHED CONSUMED. A further fault
injected inside the transaction while the scan row was being written also rolled
back, and a second consumption after a committed one lost its fence and changed
no row. [S2]

The new guarded suite grew from 44 tests at the refused head to 49 at the merged
head. One existing boundary pin had to move as a consequence — the module list
permitted to name the capability table gains the store — and that movement was
FLAGGED FOR THE OWNER rather than made quietly, with the one permitted insert
pinned to its place inside the corrected code. [S2]

8. THE REVIEW'S OTHER FINDINGS, AND WHAT EACH BECAME [S2,S4]

  P1  A release with no worker result accepted a MISSING retrieval summary,
      although the design says such a release carries one. Corrected to a
      two-directional rule: not-started means exactly no summary, no-result
      means a valid summary. Pinned in both directions, and the refusal happens
      before any statement is issued.

  P1  THE DESIGN TEXT WAS WRONG AND THE CODE WAS RIGHT. The post-restore SQL
      returns EVERY restored reservation lease, not only lapsed ones, because
      after a restore the process that held the lease no longer exists. The
      implementing session had already noticed the contradiction and recorded
      it. The review's disposition was to CORRECT THE AUTHORITATIVE DESIGN
      rather than leave code and design knowingly divergent, and to make the
      test actually execute the restore case on LIVE leases instead of only on
      lapsed ones. Both were done. This is the one finding where the evidence
      record's own observation, written before the review, was upheld.

  P1  A SECURITY CLAIM WAS TOO STRONG AND WAS NARROWED. The validator accepts
      only a lower-case slug form, and the review pointed out that SYNTAX IS
      NOT MEMBERSHIP: target-derived text can still be encoded as a legal slug.
      The claim that nothing could be smuggled through was therefore WITHDRAWN
      and restated as a shape check, with membership of the closed probe list
      assigned to the protocol boundary of a later slice. No regular expression
      was changed to make the claim true; the claim was changed to match the
      code. The probe identifier format was also aligned with the parallel
      content decision before either pull request merged.

  P2  A PROMISED COMPATIBILITY PROOF HAD BEEN OMITTED AND WAS NOT ALLOWED TO BE
      DROPPED SILENTLY. The design calls for the earlier rollback image's write
      path to be exercised against the new migration, and the first head showed
      only the current floor. The review's instruction was to run it or amend
      the design with a reviewed reason — not to quietly leave it out. It was
      run, with a control (section 10).

FOUR MATTERS WERE EXPLICITLY ACCEPTED BY THE REVIEW AS NOT BLOCKERS, and are
recorded here so that the acceptance is not mistaken for an omission: the extra
fixture change belonged to an already-declared class; the migration statement
reorder was justified by the reproduced PostgreSQL failure; the table alias in
the locking read was justified; the M13 audit failing on the newer schema was
expected; and the production-shape timing gate was allowed to REMAIN PENDING
with an explicit instruction NOT TO FABRICATE IT AND NOT TO CONTACT PRODUCTION
FOR IT. [S4]
