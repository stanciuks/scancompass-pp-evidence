4. THE MIGRATION DESIGN WAS FEASIBLE, AND THAT WAS SHOWN RATHER THAN ARGUED
   [S2]

LEGALITY. The whole draft applied as the migration role, IN ONE TRANSACTION, on
a database the repository's own runner had brought to the current schema and
whose existing operator audit printed a clean pass FIRST. Every statement
succeeded: the new table, one unique index on an existing table, three foreign
keys, five indexes of which two are partial unique, and the drop-and-replace of
one check constraint plus one new one.

One finding of detail that mattered later: a composite foreign key referencing a
plain UNIQUE INDEX rather than a unique constraint IS ACCEPTED by PostgreSQL
18.6, and the record notes the generator "may prefer to emit a unique
constraint instead; either is legal". The next milestone hit a related ordering
problem in the real generator, which this verification could not have seen
because it hand-wrote its draft.

TWENTY-FOUR SCRIPTED ASSERTIONS, ALL PASSED, AS THE APPLICATION ROLE, each
recorded WITH ITS SQL STATE AND CONSTRAINT NAME rather than with a message. In
substance they prove that the audit-first write order is STRUCTURAL and not
merely conventional — setting a lease before its run row exists is refused —
and that the schema itself refuses a run naming another account or another
domain than its entitlement, one account's lease on another's run, a second
running run, an authorisation expiring before the lease, a mismatched tier and
retention class, a completed run with no retrieval summary, an oversize summary,
a deletion of an audit row by the application role, and a change to the scope an
existing run references. They also prove the shared-lock read works as the
application role WITH NO NEW GRANT, that deleting a scan leaves the run row
intact with a nulled reference, and that the previous milestone's own revocation
and reaping of leased rows still succeed.

THE NULLING REFERENTIAL ACTION WAS PROVEN WITH THE REAL COMMAND LINE, NOT A
HAND-WRITTEN QUERY — and proven the hard way. The update privilege on the new
table was REVOKED from the application role, an expired paid scan was linked to
a completed run, and the repository's own retention command was run AS THE
APPLICATION ROLE. It deleted the scan and exited clean; the run survived as
completed with a nulled reference and its retention stamp intact, and its
capability cascaded away. The conclusion the record draws is the useful one:
THE REFERENTIAL ACTION RUNS WITH THE TABLE OWNER'S PRIVILEGES, so the update
grant the design asks for is needed only for the milestone's OWN writes. That
turned a design to-do into a proven fact and corrected the reason the grant
exists.

CIRCULAR KEYS, DUMP AND RESTORE. The insert order is ENFORCED rather than
conventional, because the reverse is refused. A database holding rows of every
lifecycle shape was dumped exactly as the project's own backup script does and
restored exactly as the previous milestone's deployment rehearsal did: exit 0,
identical row counts, and all three new foreign keys validated. The record
explains why circularity costs nothing — the dump places foreign keys after
both tables are loaded — and concludes that no deferrable constraint is needed.
The previous milestone's post-restore SQL was then run on the restored database
and left no lease behind, and the design's one additional statement closed the
still-running rows. [S2]

7. TRANSACTION-OUTCOME SEMANTICS: THE DESIGN ASKED FOR SOMETHING IMPOSSIBLE
   [S2]

The design required the implementation either to classify a commit of unknown
outcome, or to treat errors "surfacing from COMMIT" as unknown. The verification
read both transaction paths in the repository and found that NEITHER IS
POSSIBLE ON THE ONE THE MILESTONE USES.

The project's older write path has an explicit phase machine and CAN tell the
difference, but it is coupled to a write circuit breaker, so a LOGICAL refusal —
a fence failure or a key violation — would be recorded as a database-health
failure. The record concludes the new transactions should NOT use it.

The path the payment code actually uses wraps a library transaction that, on a
commit failure over a broken socket, runs a rollback on the SAME DEAD
CONNECTION, and THAT error REPLACES THE ORIGINAL. The caller therefore receives
an exception with NO PHASE INFORMATION: a pre-commit failure, a server-rejected
commit and a lost acknowledgement are all simply "an error". This was CONFIRMED
EMPIRICALLY by terminating the database backend from inside a transaction, not
inferred from reading the library.

WHAT THE VERIFICATION PUT IN ITS PLACE is stronger than what it removed,
because it starts from what the milestone actually needs. Every post-failure
action is already FENCED AND IDEMPOTENT: release matches only the exact
reservation, consumption matches only a reserved row with that exact token and
a live lease, run closures match only running rows. So no phase-accurate commit
knowledge is needed FOR SAFETY. The implementable rule became: EVERY EXCEPTION
FROM RESERVE OR CONSUME IS OUTCOME UNKNOWN — never dispatch after an uncertain
reserve, never retry and never return a capability after an uncertain consume,
and read the truth later from the fenced database state. The record also states
the honest limit: NO COMPONENT MAY CLAIM EXACTLY-ONCE. The scanner may run more
than once per entitlement over time, never concurrently, and THE DATABASE
COMMITS AT MOST ONE CONSUMPTION.

A PRE-EXISTING OBSERVATION WAS RECORDED AND DELIBERATELY NOT FIXED. Tracing the
connection-pool and client libraries showed that a connection dying between
statements while a client is checked out raises an unhandled error event, which
affects the three preceding milestones TODAY and is not this milestone's doing.
The record works out the real consequence in each context — the production web
server logs it and survives, so the transaction simply fails on its next
statement and becomes "unknown" by the rule above, while the retention command
would exit non-zero and is re-runnable — and leaves it for the owner as a
possible later hardening. NOT CHANGED HERE. [S2]

8. THE DEADLOCK FINDING, AND WHY THE NON-WAITING FORM WAS CHOSEN [S2]

The design asserted that the purge minimisation pass "holds no other lock, so it
cannot join a cycle", and that all users of the new table are disjoint. THE
VERIFICATION FOUND THAT FALSE FOR A MULTI-ROW UPDATE, and did not stop at the
argument.

THE MECHANISM: such an update HOLDS THE ROWS IT HAS ALREADY UPDATED WHILE IT
WAITS for the next one, and a retention or denylist batch does exactly the same
thing through its cascaded nulling of references. Two bounded workloads, each
holding what the other needs next.

REPRODUCED, NOT ARGUED. Retention deleted one scan, locking its run row, while
the purge pass updated a second run row; then retention deleted the second scan
while the purge reached the first — AND POSTGRESQL DETECTED A DEADLOCK and
aborted the purge. The record gives the SQL state.

THE NON-WAITING FORM, ALSO MEASURED. Selecting candidate rows with a
locking read that SKIPS ALREADY-LOCKED ROWS, then updating exactly those
identifiers, NEVER WAITS. On the same schedule it updated the free row, skipped
the locked one, and retention then completed. The record is careful about what
was and was not at stake: NOTHING IS CORRUPTED EITHER WAY, because both
commands are re-runnable — what the plain form costs is an aborted maintenance
pass, not data. But the design's claim and its disjointness argument had to be
corrected, and the next milestone was required to implement the non-waiting
form, repeated until no candidate remains. The owner later wrote the stronger
version of that into the approval: "never use the deadlocking plain multi-row
UPDATE form." [S2,S3]

THE NEXT MILESTONE WAS ALSO REQUIRED TO KEEP THE FAILURE AS A TEST — a
NEGATIVE CONTROL proving the naive form really does deadlock — so that the
reason for the awkward two-statement shape cannot be lost later. [S2]

9. THE RESOLVER TAIL, AND OTHER MEASURED LIMITS [S2]

The design described name resolution as not cancellable with a tail "measured in
seconds", and carried that as an unmeasured item. IT WAS MEASURED.

Against ONE SILENT NAMESERVER, the resolver as configured — with its retry count
left at the library default — took 40,011 ms. With the retry count set to one,
4,001 ms. The consequence the record draws: a zombie extended execution can
OUTLIVE ITS 25-SECOND BUDGET BY ABOUT 40 SECONDS PER CONFIGURED NAMESERVER,
because the stop is cooperative and there is no hard kill.

THE STOP CONDITION PASSED ANYWAY, and the record says why rather than just
concluding it: even with two silent nameservers the total is about two minutes,
far inside the ten-minute lease — more than seven times the margin — so THE
LEASE DOES NOT CHANGE. Two consequences were handed forward instead: a later
slice must bound the tail explicitly for the extended profile, by lowering the
retry count or cancelling the resolver at the deadline; and an existing source
comment calling the timeout "a hard ceiling" IS WRONG FOR THIS TAIL and must be
corrected. The free profile's resolver settings were left alone.

A SECOND, SMALLER MEASUREMENT: the existing cap on a report-sharing capability
counts every one ever created, and the existing index serves the time-windowed
count the design's access rule needs, SO NO SCHEMA CHANGE IS REQUIRED for the
daily re-open bound. [S2]

10. THE BLOCKER, THE OWNER'S DECISION, AND THE RESEARCH-ONLY SECTION

THE BLOCKER, C-1 — A PURCHASED REPORT COULD NOT BE SHOWN TO ITS OWNER. The
verification checked the design's access rule against the REAL report code and
confirmed six of its claims individually: existing shares stay resolvable after
every management capability is revoked; a revoked capability can neither create
a share nor request an email, each refused under the scan lock; a new capability
cannot revoke shares made by an older one; the daily bound is servable from
existing data with no schema change; the free scan's semantics stay untouched
provided the revoke-all path is reachable only for the paid tier; and the one
privilege the rule needs is already granted.

AND THEN FOUND THE WHOLE SURFACE UNUSABLE. In the existing code a management
capability can ONLY create a share, revoke a share and request an email.
VIEWING, HTML DOWNLOAD AND PDF ALL REQUIRE A SHARE CAPABILITY. The free scan
avoids the problem by returning its report inline. The access route as designed
returned only a management capability, so the owner's own page had NO WAY TO
DISPLAY THE PAID REPORT without first creating a share — and the share cap
counts EVERY SHARE EVER CREATED, revoked ones included. After at most five
re-opens, the purchased report could NEVER BE DISPLAYED, DOWNLOADED OR PRINTED
AGAIN for the rest of its retention. The record lists the three places in the
design this contradicts, and states: "NOT REDESIGNED HERE." Three options were
laid out with their costs, and the work stopped. [S2]

THE OWNER CONFIRMED IT INDEPENDENTLY BEFORE DECIDING. Comment 6102701145 on the
design pull request records the owner spot-checking the blocker against current
source — that the download path resolves a share capability while a management
capability authorises only management operations — and concluding "C-1 is real".
The owner recommended the minimal-surface option and then approved it in comment
6102736390, requiring the eight other corrections to be incorporated. THE
DECISION AND ITS CONSTRAINTS BELONG TO THE DESIGN MILESTONE and are recorded in
its own note. [S1,S3]

THE PURGE RETENTION CHOICE WAS FOUND IMPLEMENTABLE, AND THAT WAS CAREFULLY NOT
TREATED AS APPROVAL. The verification listed the minimum changes at each layer
and, separately, EVERY CURRENT PUBLIC AND OPERATOR STATEMENT THAT WOULD NEED
AMENDING — the public opt-out text, two retention passages, two runbook
procedures and two design principles — and noted one page that does NOT
conflict. Its conclusion is a boundary, not a recommendation: the wording
remains an owner, legal and privacy decision. The owner's later approval drew
the same line (section 12 of the design note). [S2,S3]

ONE SECTION WAS RESEARCH ONLY, AND IS SUMMARISED HERE WITHOUT OPERATIONAL
DETAIL. The verification examined how the production application checkout
