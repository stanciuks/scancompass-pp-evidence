2. WHAT THE DESIGN IS FOR, AND WHAT IT PUT OUT OF SCOPE [S2]

The milestone it designs lets an authenticated account that has ALREADY PROVED
it controls an exact hostname spend one purchased entitlement on one deeper
assessment of that hostname, and keep the resulting report for a bounded time.

The design's own non-goals are stated as firmly as its goals, and they matter
more than the goals for judging what was locked:

  no change whatever to the anonymous free scan, its admission, cache,
    denylist handling, rate limits, worker protocol or report lifecycle —
    payment and entitlement state never reach it
  no new payment behaviour: M14 creates no order, calls no provider, issues no
    refund and does not alter the webhook
  no subscription, bundle, credit, balance or transfer — one entitlement, one
    assessment
  NO WIDENING OF HOSTNAME IDENTITY: the exact canonical hostname only, with no
    subdomain coverage bought by purchasing a registrable domain
  no sensitive-file exposure probing, which an unresolved methodology review
    and a standing project hard gate forbid; the design neither implements nor
    promises it
  no port beyond 80 and 443 and no change to the scanner's egress firewall
  no technique from the methodology's forbidden class IN ANY TIER —
    "authorisation widens what is observed, never the class of technique"
  no automatic re-run, no renewal and no extension of a lease or an entitlement
  no production action and neither deployment decision

3. THE CENTRAL SAFETY RULE: TIER IS NOT AN INPUT [S2]

The design's load-bearing security property is that the assessment tier is
DERIVED SERVER-SIDE FROM VERIFIED AUTHORISATION and can never be supplied by
anyone. It is inherited as a binding invariant from the project's existing
security model: never from a body, query, header or cookie, and no debug flag
grants the extended tier.

The design makes that structural rather than merely asserted. The builder for
the extended command is to live in ONE module reachable ONLY from the M14
orchestrator, which reaches it ONLY after a reservation it holds has committed.
Boundary tests are specified to assert that the import closure of the free scan
route, the report routes, the launch controls and the result cache contains
neither the extended module nor any payment module; that the M14 request body
schema is strict and HAS NO FIELD that could name a tier, profile, depth,
product, entitlement, reservation, price or budget; and that no environment
variable, header, query or debug flag reaches the profile choice.

The design states the consequence plainly: "Tier is therefore not a value
anyone supplies: it is the fact that execution reached the extended command
builder." [S2]

4. AUTHORISATION AND ENTITLEMENT KEPT SEPARATE [S2]

The design inherits sixteen binding invariants from the two preceding
milestones and lists them before it designs anything. The first is the one the
whole milestone turns on: AN ENTITLEMENT IS NOT SCANNING AUTHORITY. Using one
requires the authenticated account, the exact canonical hostname AND a current
domain authorisation, re-checked at reservation AND AGAIN at consumption.

Three further boundaries were designed rather than assumed:

  THE AUTHORISATION MUST OUTLAST THE LEASE at reservation time, so that a run
  near the authorisation's own expiry is refused up front instead of being
  performed and then discarded.

  THE RE-CHECK MUST HAPPEN INSIDE THE TRANSACTION. The existing authorisation
  function takes a pool-level connection and does one non-locking read, so
  calling it before the transaction would leave a revocation able to commit
  between the check and the consumption. The design therefore specifies a new
  in-transaction variant taking a SHARED LOCK on the authorisation row,
  sharing one private rule with the existing function, taking NO clock
  parameter and reading its clock AFTER the locking read. This departs from the
  letter of the earlier milestone's instruction, and the design says so and
  puts it to the owner rather than deciding it.

  WHAT IS DELIBERATELY NOT RE-CHECKED is listed too, so the omissions are
  visible rather than accidental.

The design also records the residual window it cannot close: a revocation after
the reservation commits does not stop a worker already running, so traffic
continues for up to the budget plus the uncancellable name-resolution tail.
NOTHING IS CLAIMED TO BE RETROACTIVELY UNAUTHORISED. [S2,S4]

5. THE THREE TRANSACTIONS, AND THE LOCK ORDER [S2]

Three database transactions were designed in step-numbered detail, with a
fourth hygiene pass:

  RESERVATION (R). Under the account lock, reap any lapsed lease FIRST by the
  exact existing rule, re-check authorisation under a shared lock, insert the
  durable audit row for the run, and only then set the lease — so the audit
  record exists BEFORE any outbound paid work. A fresh fencing token, the
  reservation time and the lease expiry are written together.

  FENCED EARLY RELEASE (L). Returns a LIVE lease when the run provably produced
  nothing and provably cannot still be producing anything. The design flags
  this as a departure: the earlier milestone's state diagram labels that
  transition only for a LAPSED lease. It is put to the owner as its own
  decision rather than slipped in.

  CONSUMPTION (C). Moves the entitlement to consumed IN THE SAME TRANSACTION
  that persists the durable paid report, fenced on the row identity, the
  reserved state and the exact reservation token, and DELIBERATELY NOT on the
  lease expiry. Zero rows matched means fail closed and NEVER RETRY.

  HYGIENE. A later pass closes runs that never reported back, once their lease
  has lapsed.

THE LOCK ORDER WAS EXTENDED RATHER THAN REDEFINED, with a cycle proof, and with
one rule the first draft got wrong: re-writing a row the transaction ALREADY
HOLDS is not a new acquisition. Without that rule a literal enforcement would
have refused the design's own writes (section 9, finding 4).

The closed set of outcomes for a run — consumed, two kinds of release,
authorisation lapsed, two kinds of lost fence, and abandoned — is specified as
a database constraint, and the design states that adding an outcome is a
reviewed migration. [S2]

6. THE LEASE AND THE FENCING REQUIREMENTS [S2]

The lease was sized from the bounds that already existed rather than chosen:

  extended scan budget            25,000 ms, the same as the free scan, so the
                                  synchronous request stays inside the existing
                                  web-server read timeout and no timeout or
                                  worker ceiling changes
  orchestrator execution deadline 120,000 ms, a monotonic hard deadline from
                                  the committed reservation to the START of
                                  consumption
  LEASE                           600,000 ms (10 minutes), A COMPILED CONSTANT
  renewal                         NONE

The ten minutes are justified in both directions: long enough that a legitimate
run is never refused at consumption for a lapsed lease — the expensive failure,
where the work is done and the report thrown away — and that any zombie worker
execution is long over before a new reservation can start; short enough that a
crashed run returns the purchase within minutes.

WHY A CONSTANT AND NOT CONFIGURATION, in the design's own reasoning: the lease
is a correctness parameter tied to compiled bounds, and a configuration value
can be set below them, "turning every slow run into a discarded result".
Compile-time assertions are specified to tie the lease to the deadline, the
write budget and the worker timer.

Fencing is required at every point where a lease could be mistaken for another:
the reservation token is the run's identity and the audit row's primary key, so
"the lease and its audit row cannot drift"; consumption and release both match
on the exact token; and replaying a stale run's completion is listed in the
abuse model as a threat the token answers. [S2]

7. THE MIGRATION THAT WAS DESIGNED AND NOT CREATED [S2]

The design reserves the name and the contract string, and states in its own
heading that the migration is NOT CREATED in M14-0.

THREE SHAPES WERE CONSIDERED FOR THE PAID ARTIFACT AND TWO WERE REJECTED WITH
REASONS. The obvious one — a column on the entitlement pointing at the scan —
was rejected because EVERY POSSIBLE REFERENTIAL ACTION FAILS: refusing the
delete would abort the retention batch in this image and in every older image
on rollback; cascading would delete financial history with the table owner's
privileges; nulling it would destroy the very fact the column exists to prove.
Duplicating the report tables for paid reports was rejected as duplication for
no safety gain. The chosen shape puts report CONTENT in the existing tables, so
it is retention-deleted like any report, and puts the commercial and audit fact
in a new table NOTHING IN THE APPLICATION CAN DELETE.

The planned change, as designed: one new table whose row is the durable audit
record of one lease; a widened check on the scan tier; a new check coupling the
tier to its retention class; one unique index on the entitlements table; and
three foreign keys, two of them composite, one nulling its reference on delete
and two refusing it. The design also records what the migration DELIBERATELY
DOES NOT CONTAIN: no new entitlement state, no change to the payment tables, no
trigger, no data migration, and no destructive change but the one check
constraint it immediately replaces with a superset.

The predicted catalogue counts were written down BEFORE anything was measured,
which is what later let a verification confirm them rather than derive them
(section 11). The design states the additive-and-widening property as something
"to be proven, not assumed". [S2]

8. WORKER PROTOCOL VERSION 2, RETENTION AND OWNER ACCESS [S2]

THE SCANNER ISOLATION BOUNDARY WAS NOT WIDENED. A second worker service was
considered and rejected: the existing worker already IS the isolation boundary,
and both tiers must obey identical network policy. A client-visible tier
parameter was forbidden outright. What was chosen is a second protocol version
on the existing worker command, adding one REQUIRED profile field with no
default, whose value the web tier sets from the code path that admitted the run.
The worker maps the profile to a WORKER-OWNED check set and budget ceiling, so
the command still carries no path, port, resolver, timeout or check list. Both
protocol versions are to be accepted during the milestone so the web and worker
images can roll independently and the free path need not change in the same
slice.

RETENTION AND OWNERSHIP. The paid report is to be kept 90 days and owned
THROUGH the new audit table, because the scans table has no account column and
"gets none". The design works out what survives what — retention, a denylist
purge, a reversal after consumption, an account deletion, a database restore —
in a table, and it states the uncomfortable consequence rather than burying it:
once a paid assessment exists for a hostname, a denylist purge NO LONGER
REMOVES EVERY SCAN-DERIVED RECORD for it. That consequence became the privacy
decision of section 10.

OWNER ACCESS WENT THROUGH TWO FULL REDESIGNS inside this milestone (sections 9,
10 and 11) and ended as a single authenticated route with a strict three-value
action enum: view, download as HTML, download as PDF. Its final shape, and the
reason the two earlier shapes failed, are recorded in section 11.

9. THE INDEPENDENT ADVERSARIAL REVIEW OF THE FIRST DRAFT [S2,S4]

An independent read-only review of the first draft, against the preceding
milestone's contract and the real code, found NO BLOCKER and TEN DEFECTS, all
corrected in place. It also VERIFIED several things the draft had claimed,
including the lock-cycle proof, the lock modes the new keys would produce, the
behaviour of the coherence check under a nulled reference, and the insert order.

The ten, in the design's own correction log, are worth recording because several
are errors of over-claiming rather than mechanism:

  1  Release was described as "the reap applied early" adding no new
     transition. It is not: the existing rule moves a lease back only when it
     has LAPSED, and release does it to a LIVE one. Rewritten as a new guard
     on an existing edge and put to the owner as its own decision.
  2  The draft said no binding earlier decision was contradicted, and that the
     authorisation check used the same rule "at the transaction's now". Both
     were wrong: three departures existed and are now listed in the header,
     and a clock read before a locking read can be stale — which is exactly
     what the existing module exists to forbid.
  3  "It changes nothing for M13 code" was false, because existing FIXTURES
     hand-insert leases the new key would refuse. The carve-out is now
     explicit, and the stop condition was narrowed to RUNTIME write paths.
  4  "The lock order is enforced at runtime" would have refused the design's
     own writes; the held-row exemption was added.
  5  A claim about sharing shortening a long retention was wrong in mechanism;
     the real effect is that a paid report cannot be shared or emailed after
     its ninetieth day, in every image.
  6  The audit row did not actually satisfy the inherited "what was retrieved"
     requirement; a bounded, content-free retrieval summary was added.
  7  Access re-mints were called "harmless" because of an existing cap. The cap
     counts EVERY token ever minted, so about a hundred re-opens would have
     LOCKED THE OWNER OUT of their own paid report. (This fix was itself later
     found not implementable — section 10.)
  8  "Nothing is retroactively unauthorised" was too strong; the residual
     window is now stated.
  9  The new key was said to make the durable-report guarantee a database fact.
     It proves a run row exists, not that it completed; the other half is
     "code + audit".
  10 Ten smaller internal inconsistencies, each corrected.

10. THE OWNER'S REVIEW: TWO BLOCKERS AND A PRIVACY DECISION [S3]

The owner's review of head 7953ac0 (comment 6095441232) recorded that the
continuous integration was green and the documentation-only scope clean, called
the design "strong overall", and said: DO NOT MERGE YET.

  BLOCKER 1 — AN INVARIANT WAS FALSE AS STATED. The design called "a paid
  report exists if and only if its entitlement is consumed" a GUARANTEE, while
  another section deliberately deletes paid report content at retention or on a
  purge while the entitlement stays consumed. The owner's objection was not a
  wording nit and said so: "it changes the invariant the schema is meant to
  prove." The required correction was to state the contract in THREE TIERS — at
  the consume commit a durable report is persisted atomically with the state
  change; historically, consumed proves a report WAS committed, through the
  retained audit row; after retention or purge the report may be gone while the
  entitlement and the audit row remain — and to keep "no consumption without a
  durable report at commit" as the actual atomic guarantee.

  BLOCKER 2 — A DESIGNED TRANSACTION COULD NOT BE IMPLEMENTED ON THE EXISTING
  SCHEMA. The access transaction was specified to revoke previously
  ACCESS-MINTED management tokens while preserving a distinct consumption
  token. The owner checked the real table and found it has NO PURPOSE OR SOURCE
  COLUMN, so "access-minted" rows cannot be identified: "Do not leave a
  non-implementable middle state." The owner's recommended minimal design —
  revoke ALL unrevoked tokens for that paid scan under the scan lock and mint
  exactly one — was adopted, which needs no schema change.

  OWNER DECISION — PRIVACY. The owner required that the purge consequence of
  section 8 be made explicit and reconciled with the project's existing public
  promises before implementation: audit the current public and operator
  wording, state exactly what is retained and why, and "if current public
  wording promises full deletion, mark the wording change as an
  owner/legal/privacy blocker RATHER THAN SILENTLY VIOLATING IT". The retrieval
  summary was also to be narrowed to the minimum content-free audit facts.

The same comment listed NINE AREAS IT FOUND NO BLOCKER IN, which is recorded
here so the acceptance is not mistaken for silence: the reserve-before-outbound
shape, fencing and consume atomicity, the refund and dispute races, the lock
order, the referential-action concept — still to be proven on the real database
under the application role — provider-mode isolation, free-scan isolation, the
honest non-exactly-once contract, and the ten-minute lease as a default. [S3]

11. THE VERIFICATION'S BLOCKER, THE OWNER'S DECISION, AND A SECOND REFUSAL

M14-0 DID NOT MERGE NEXT. Between the corrections and the merge, a separate
documentation-only milestone verified the design against the real repository
and a real database; it has its own Personal Project record, named at the end
of this note, and it merged FIRST, on 2026-10-10. Its one blocker and eight
corrections then had to be absorbed into this design before the lock was

THE BLOCKER, C-1 — THE PURCHASED REPORT COULD NOT BE SHOWN. The verification
found that in the existing code a management token can do exactly three things:
create a share, revoke a share it created, and request an email. VIEWING, HTML
DOWNLOAD AND PDF ALL TAKE A SHARE TOKEN. The access route returned only a
management token, so the owner's own page had no way to display the paid report
without creating a share — and the share cap counts EVERY share ever created,
revoked ones included. After at most five re-opens the purchased report could
never be displayed, downloaded or printed again for the rest of its retention.
The verification DID NOT REDESIGN IT; it laid out three options and stopped.
[S2,S4]

THE OWNER INDEPENDENTLY CONFIRMED THE BLOCKER BEFORE DECIDING. Comment
6102701145 records the owner spot-checking it against current source and
concluding "C-1 is real". The owner then decided it in comment 6102736390:
OPTION B APPROVED — the authenticated access route becomes the owner's access
surface with a strict server-controlled action enum; view returns the verified
report plus one fresh management token under a revoke-all-and-mint-one rule;
the two download actions render the retained frozen report with the EXISTING
renderers and CREATE NO SHARE ROW. The owner added two constraints that read as
refusals of the easy fix: "do NOT add extra route files solely for owner
viewing/download", and "Do not raise the five-share cap merely to make owner
access work." [S3]

THE SAME OWNER COMMENT REQUIRED EIGHT FURTHER CORRECTIONS, C-2 TO C-9, to be
incorporated into the design. Their substance belongs to the verification
record and is summarised there; what matters for this note is that they changed
the LOCKED DESIGN, not just an evidence file: the purge pass was respecified in
