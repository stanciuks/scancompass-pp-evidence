2. WHAT M14-2.3 IS, AND WHAT IT IS NOT
================================================================================

WHAT IT IS. The step that makes the scanner engine take an assessment profile
as an argument, and makes the catalogue tier a DERIVED CONSEQUENCE of that
profile rather than something a caller can state. Under the free profile the
engine behaves exactly as it did, byte for byte. Under the paid profile it
computes the same forty-two free results with the same semantics, performs
exactly two additional lookups, assembles the facts the step-2.2 primitives
extract, and returns a DRAFT that nothing downstream will accept. [S2]

WHAT IT IS NOT. Not one of the ten paid checks. Not a catalogue entry, a content
entry, an evidence-policy entry, a priority methodology or a report composition
for the paid tier — those are steps 2.4 through 2.6. Not a worker protocol
change, which is M14-3. Not a route, an entitlement or an orchestration, which
is M14-4. Not a change to any network, redirect, address, resolver or
authorisation policy. Not a fix for any of the four measured free-path findings.
Not a schema or migration change. [S2]

THE DESIGN'S OWN NAME FOR THE ENGINE OPERATION WAS ALREADY TAKEN, and the slice
renamed its own entry point rather than shadow the existing one. A function of
the design's chosen name already existed in the web layer and is named in the
project's boundary rules. Introducing a second export of the same name in a
different layer was judged worse than renaming, so the engine entry point
carries a distinct name and is documented in place as the design's conceptual
operation. THE FREE ENTRY POINT IS KEPT AS A ONE-LINE WRAPPER around the new
one, so EVERY EXISTING CALLER — the worker above all — IS UNCHANGED. [S2]

THE PAID RETURN VALUE IS DELIBERATELY INCOMPLETE, AND THAT IS THE POINT. No
paid catalogue version exists yet; asking for one throws. The implementing

than invent a placeholder. The consequence is structural: the draft is not
assignable to the free result type, so the compiler refuses to hand it to report
composition or to the worker result schema, and a test pins that refusal. IT IS
THEREFORE NEVER "A COMPLETE PAID REPORT", AND NOT BECAUSE ANYONE PROMISED NOT TO
TREAT IT AS ONE. [S2,D1]

6. THE FIVE OUTCOME STATES, AND WHAT NONE OF THEM MAY BECOME
================================================================================

THE SLICE GIVES EACH OF THE TWO LOOKUPS FIVE POSSIBLE OUTCOMES, AND THIS SESSION
READ ALL FIVE IN SOURCE. [R1,S2]

  PRESENT        issued and answered, a record was found
  ABSENT         issued and answered, and the answer was a genuine absence
  FAILED         issued and answered with a failure — a resolver timeout, a
                 server failure, a refusal, or a resolver that threw or
                 rejected in breach of its own contract
  NOT_ATTEMPTED  the scan deadline had ALREADY EXPIRED before the wave began,
                 SO NO QUERY WAS SENT AT ALL
  ABANDONED      the query WAS SENT, but the deadline fired before an answer
                 arrived; any later answer is DISCARDED

EXACTLY ONE OF THE FIVE IS AN ABSENCE, AND THE SOURCE IS EMPHATIC ABOUT IT. Only
ABSENT means "there is no record". A resolver timeout is a FAILURE, NEVER an
absence. A resolver that breaches its contract by throwing is CONTAINED TO ITS
OWN SLOT as a failure, so it cannot fail a paid run that a free run would have
survived. THE TWO DEADLINE STATES ARE NOT ABSENCES EITHER, AND THE SOURCE
FORBIDS THEM EVER BECOMING ONE. [S2]

THE PROHIBITION IS WRITTEN IN THE SOURCE ITSELF AND REPEATED IN THE STEP-2.4
PLAN, IN BOTH PLACES AS A STOP CONDITION. Neither deadline state may ever map to
an absence, to a warning that says "not published", or to a pass. A deadline
state or a failed lookup reaching any of those three IS A STOP. [S2]

THESE ARE INTERNAL ENGINE FACTS AND NOT STATUS TOKENS, AND THE MAPPING IS NOT
THIS STEP'S TO MAKE. The step-2.4 plan records TWO PRECEDENTS FROM THE EXISTING
FREE SCAN for how a deadline-curtailed retrieval is reported, lays them out as
two named options for the step-2.4 reviewer, AND CHOOSES NEITHER. It states
explicitly that this is NOT one of the five open owner decisions and is written
down SO THAT IT IS NOT DECIDED SILENTLY. It further requires that whichever
option is chosen, the new oracle rows for it ENTER AS PROPOSED AND BE REVIEWED.
[S2]

THE DEADLINE IS A TIMER, AND THE SOURCE IS PRECISE ABOUT WHAT A TIMER CANNOT
DO. The scan budget is unchanged. A platform resolver query TAKES NO CANCEL
SIGNAL, so an already-issued query RUNS ON TO ITS OWN RESOLVER TIMEOUT after the
