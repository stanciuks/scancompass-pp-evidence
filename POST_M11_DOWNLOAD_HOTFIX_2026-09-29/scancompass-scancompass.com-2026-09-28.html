Priority actions

MEDIUM1. Email impersonation protection is incomplete

SPF and DMARC work together to stop spoofed mail from reaching an inbox: SPF declares who may send, and DMARC decides what happens when a message fails that check. A gap in either one leaves the domain easier to spoof in phishing and business-email-compromise attempts, even if the other is configured well.

  • MEDIUMSPF policy strictness — Change the SPF record's terminal mechanism to `-all` once all legitimate sending sources are correctly listed in the record.
  • MEDIUMDMARC enforcement level — Move the DMARC policy to `p=quarantine` and, once reports confirm legitimate mail is authenticating cleanly, to `p=reject`.
LOW2. CAA records

CAA is a hardening opportunity, not a vulnerability. Publishing it narrows which certificate authorities can ever issue for this domain, reducing the chance of a mis-issued certificate. Its absence is extremely common and is not itself a risk.

Publish a CAA record at the domain's apex naming the certificate authority (or authorities) actually used, e.g. `example.com. CAA 0 issue "letsencrypt.org"`.

How to verify: Query the domain's CAA records and confirm they list the expected certificate authority.

LOW3. HTTPS enforcement could be hardened further

HTTPS is available here — this is about the layers that keep visitors on it. A missing HTTP-to-HTTPS upgrade leaves a visit that begins at http:// exposed until encryption is established. A missing HSTS policy means a browser is never given a standing instruction to use HTTPS by itself. A policy that is present but short-lived expires sooner than SCANCOMPASS's strong-retention threshold, so that instruction has to be refreshed more often to stay in force.

  • LOWHSTS policy strength — Raise the `max-age` on the `Strict-Transport-Security` header as you gain confidence that every HTTPS endpoint for this site is stable — a deliberately short value during rollout is a reasonable precaution, since it limits how long a mistake would persist. SCANCOMPASS treats 180 days (15552000) as a strong retention period. `includeSubDomains` is a separate decision about scope, and browser preload is a separate opt-in with its own requirements (a one-year `max-age`, `includeSubDomains`, and the `preload` token) that is deliberately hard to reverse — neither is required for this control.

LOWHSTS policy strength

WARNING · HEADERS · HEADERS.HSTS_MAX_AGE

HSTS is enabled, but browsers only remember it for 5 minutes.

The policy itself is valid and working — this is about how long it persists. Once the period lapses, a browser that has not returned since forgets the instruction, so if that visitor next arrives over `http://` — a typed address, an old link, a bookmark — the browser no longer upgrades the request automatically until it sees the header again. Longer retention keeps the protection in place between visits. SCANCOMPASS treats 180 days as its strong-hardening threshold for this control; that is a grading policy of ours, not a minimum set by the HSTS standard.

What we checked:

How long the HSTS policy's `max-age` tells browsers to remember to use HTTPS.

Why it matters:

A short max-age means the protection expires quickly between visits, giving an attacker a wider window if a visitor hasn't been back recently.

How to fix it

Raise the `max-age` on the `Strict-Transport-Security` header as you gain confidence that every HTTPS endpoint for this site is stable — a deliberately short value during rollout is a reasonable precaution, since it limits how long a mistake would persist. SCANCOMPASS treats 180 days (15552000) as a strong retention period. `includeSubDomains` is a separate decision about scope, and browser preload is a separate opt-in with its own requirements (a one-year `max-age`, `includeSubDomains`, and the `preload` token) that is deliberately hard to reverse — neither is required for this control.

How to verify

Reload the site over HTTPS and confirm the header's `max-age` value has increased.

INFOObsolete TLS versions

PASS · TRANSPORT · TRANSPORT.TLS_VERSION_MIN

Obsolete TLS versions are refused.

The endpoint we tested explicitly rejected both TLS 1.0 and TLS 1.1. This is an external check against one published address for this hostname, so it reflects the endpoint we reached rather than a guarantee about every server behind the name.

What we checked:

Whether the server still completes a connection when a client offers only TLS 1.0 or only TLS 1.1. We attempt one handshake per obsolete version against one published address for this hostname, and record what the server actually did.

Why it matters:

TLS 1.0 and 1.1 are formally deprecated and have known weaknesses that TLS 1.2 and 1.3 fix. A server that still accepts them lets an attacker who can influence a connection push a visitor down onto the weaker protocol, undoing protections the modern versions provide.

How to fix it

Set the minimum accepted TLS version to 1.2 in the web server or TLS-termination configuration (for example `ssl_protocols TLSv1.2 TLSv1.3;` in nginx, or the equivalent setting at your CDN or load balancer). This is a protocol setting — replacing or renewing the certificate does not change which versions are accepted.

How to verify

Re-run this check and confirm both obsolete-protocol handshakes are refused. The certificate does not need to change for this to be fixed.
