7. DEVIATION TWO — A VISUAL DEFECT, AND THE GATE STAYED CLOSED

During closed-gate visual acceptance the owner found that the header theme
button read "Light theme" in BOTH the dark and the light state. Switching
worked and persisted; the label did not move. [R1]

PRODUCTION REMAINED SCAN-CLOSED WHILE IT WAS FIXED. The defect was not
accepted, and the gate was not reopened to get past it. [R1]

Root cause and fix, from the source record: the visible text was a literal and
the accessible name was a constant, so the only state-varying attribute was a
pressed state, which is invisible on screen. PR #30 makes the control name the
ACTION — "Light theme" while dark, "Dark theme" while light. THE PRESSED STATE
WAS REMOVED RATHER THAN KEPT beside the new name, because a pressed state
qualifies a name as a state: with an action name, light mode would have
announced the dark theme as pressed, which is precisely what is not on. The
filled visual state moved to a theme data attribute, so the semantics changed
and the appearance did not. [S2]

The owner confirmed the corrected control in production before scanning was
reopened. [R1]

THE RATE WAS MEASURED RATHER THAN ESTIMATED. The capability is 32 random bytes,
43 base64url characters, and the scan folded case before searching, so each of
the three forbidden letters could match in either case. Two hundred thousand
tokens were put through the same message shape: the old assertion would have
failed 249 times — 0.124 %, about one run in eight hundred — and every one of
the 249 was the same three-letter term, the only one short enough to be
realistically reachable. The corrected assertion failed 0 times in the same
200,000. [S3]

WHAT THE CORRECTION CHANGED IS THE PROPERTY, NOT THE THRESHOLD. The test now
excludes ONLY the exact opaque payload — the challenge identifier and the token
— from the semantic scan, by splitting on that literal rather than by a
pattern, so no character of a random token can be read as one. STILL INSPECTED,
DELIBERATELY: the subject, every line of authored prose, the link's origin and
path, and the fragment marker itself; the notification that carries no
capability is still inspected WHOLE, and the test proves that by asserting the
redacted copy is byte-identical to the raw copy in that case. The separate
assertions about where a capability may and may not appear are untouched. [S3]

IT IS PINNED BOTH WAYS. A committed deterministic fixture — a valid 32-byte,
43-character capability that CONTAINS the forbidden term — reproduces the old
false positive on demand, and a second regression plants real forbidden wording
in the subject and in prose directly beside the link and requires the scan to
find it, so the exclusion cannot be hiding a genuine occurrence. Making the
exclusion a no-op fails three tests, including the deterministic regression, so
it does not pass regardless of the fix. The fixture value is NOT reproduced in
this note. [S3]

NO RUNTIME SOURCE CHANGED, no deployment followed, and production remained on
the already accepted R1 images. The authored message copy was clean throughout:
the two forbidden terms that appear in the mail module at all are in docblock
comments stating the rule the module follows, and neither reaches a built
message. The deployed functional source is still a3d3a47…; main's current head,
bdbe2820…, is R1's docs plus this test correction and changes no runtime
behaviour. [S1,S3]
