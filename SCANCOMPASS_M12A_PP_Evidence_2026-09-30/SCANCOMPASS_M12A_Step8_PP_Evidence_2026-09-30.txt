REAL DEFECT DISCOVERED BY THIS GATE
The consolidated production build exposed an M12A-7 integration defect.

Next compiles src/instrumentation.ts for both the Node and Edge runtimes. The M12A-7 scanner
readiness reporter was a top-level function that dynamically imported worker-readiness.ts itself.
Turbopack traced that import while building the Edge branch and reached worker-readiness.ts's
node:http import.

Build warning:
A Node.js module is loaded ('node:http') which is not supported in the Edge Runtime.

The build still completed, which is why the earlier step did not fail outright, but the warning
showed that the Edge instrumentation trace had crossed into a Node-only raw-network module.

FIX
Both persistence and scanner-readiness module import expressions now sit lexically inside the:
NEXT_RUNTIME === "nodejs"
guard.

Each detached reporter receives a loader function and performs the load inside its own try block.

This preserves:
- task-owned import failure handling;
- detached execution;
- exactly-once logging;
- three-way independence;
- worker readiness remaining outside launch controls.

A structural test now pins that both value-position readiness imports remain inside the Node
runtime guard and do not reappear inside the top-level reporters.
