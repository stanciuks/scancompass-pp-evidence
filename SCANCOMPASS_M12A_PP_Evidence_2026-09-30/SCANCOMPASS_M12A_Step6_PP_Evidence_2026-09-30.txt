PURPOSE
Represent the scanner worker as a separate production Compose service and divide network/environment
authority between the web tier, scanner worker, database and optional notification provider.

FINAL SERVICE TOPOLOGY
1. app
2. scanner
3. db
4. retention (profile-gated maintenance service)

FINAL NETWORK TOPOLOGY
1. db_internal
   - internal: true
   - members: app, db, retention

2. scan_internal
   - internal: true
   - members: app, scanner
   - private command channel

3. scanner_egress
   - ordinary bridge with gateway
   - member: scanner only
   - fixed IPv4 IPAM:
     subnet 10.83.6.0/29
     gateway 10.83.6.1

4. notify_egress
   - ordinary bridge with gateway
   - member: app only
   - exists for the application's pre-existing provider subsystem

`app_egress` was removed.

DATABASE / RETENTION ISOLATION

DEFAULT ROUTING
- app default route explicitly points through notify_egress.

FIXED SCANNER EGRESS SUBNET
scanner_egress uses 10.83.6.0/29.

Reason:
M12A-10 will need a stable subnet to identify scanner traffic at the host firewall boundary.
A dynamically selected Docker subnet could change after network recreation and silently invalidate
a host rule.

This step did NOT claim that the chosen subnet cannot conflict with every route on the eventual
host. That must be established by later disposable/production acceptance.

IMPORTANT THREAT-MODEL CORRECTION
Owner review found two descriptions in the first M12A-6 commit that were stronger than Docker
actually guarantees.

Incorrect claim 1:
"No ports mapping means the worker is unreachable from the Docker host."

Corrected truth:
- port 8787 is not published onto a host TCP port;
- it is not exposed through Docker port publishing or Nginx;
- but the Docker host can still route to container addresses on an ordinary bridge.
Therefore the property is "no host-published port", not "the host cannot reach the worker."

Incorrect claim 2:
"No service holds both general egress and a database credential / the app lost general egress."

Corrected truth:
- notify_egress is an ordinary non-internal bridge;
- therefore the app still has network-layer Internet connectivity and still carries its DB
  credential;
- the important change is that scanner target execution no longer runs in that credential-bearing
  process and the app no longer shares scanner_egress.

The corrected security statement is:

No credential-bearing web process shares the scanner's dedicated target-egress network, and the
hostile-byte worker holds no application, database or email credentials.

The corrective commit changed documentation/tests only. Mechanical comparison showed all 154
active non-comment Compose lines were identical before and after the correction.

WHAT THIS STEP DOES NOT CLAIM
- scanner host-level egress is NOT yet restricted;
- scanner_egress is an identifiable bridge, not a destination firewall;
- scan_internal is topology, not authentication;
- app compromise is NOT network-confined to the email provider;
- Docker-host/root compromise is outside this container-isolation boundary.

M12A-10 owns host-level egress enforcement and E1–E23 proof.
