2. PURPOSE

Decide how payments are switched on, where the commercial configuration lives,
and how the application talks to Stripe — before anything can be reached from a
browser. [S2,S5]

3. THE CONFIGURATION SPLIT, WHICH IS THE WHOLE POINT OF THIS STEP

Payments are off unless an operator sets a flag to exactly the raw value "1".
" 1 " and "true" stay CLOSED, deliberately, because for a boundary where
"accidentally on" means real money the strictest reading is the right one.

There are two independent switches, and the gap between them is the valuable
part:

  payments surface off          both payment routes do not exist at all
  surface on, selling off       NEW PURCHASES REFUSED, but refunds and
                                disputes for past purchases are still recorded
  surface on, selling on        normal operation

The middle row is "STOP SELLING, KEEP RECONCILING", and this step is where it
stopped being an intention and became structural. The configuration is split
into three functions with DISJOINT inputs: the webhook half reads the declared
mode and the signing secret and NOTHING ELSE — not the API key, not the price
identifier, not the public web address. A deployment that has retired its
Stripe key, or lost its price configuration, can therefore still record a
refund it owes a customer. A first draft had put all of it in one place, which
would have made the middle row untrue in exactly the case it matters. [S2,S5]

4. THE MODE IS DECLARED, NOT INFERRED FROM THE SECRET

An earlier abandoned attempt at payments derived test-versus-live from the shape
of the API key. This step declares the mode in configuration and CROSS-CHECKS
the key against the declaration. The reasoning is recorded: deriving the mode
from a secret means THE SECRET DECIDES THE BLAST RADIUS, so pasting a live key
into a test deployment would silently convert it into a live one. With a
declared mode, a key swap alone produces an invalid configuration, which fails
closed. A live credential with the live interlock closed also fails closed. [S2]

5. ONE PROVIDER ENDPOINT, AND ONE PLACE THAT MAY REACH THE NETWORK

The project writes its own narrow Stripe adapter rather than adding the vendor
software-development kit, and the decision was re-made on current grounds rather
than inherited. The whole provider surface is ONE outbound request —
creating a hosted checkout session.

Exactly one file in the entire payments tree may call the browser-style network
function, and it is pinned by an automated boundary test: one compiled-in web
address, one literal path, no parameter that could move the destination, the
destination re-checked by exact equality immediately before dispatch, and
redirects refused. The adapter writes exactly twelve named request fields and
accepts no general field map, so no value can reach Stripe through a field
nobody reviewed. The payer's email address is deliberately NOT sent. [S2,S5]

Both Stripe API versions are pinned as compiled-in constants rather than
configuration — the one the application sends, and the one it requires inbound
messages to be formatted as — because a configuration change must not be able
to alter how a payload is interpreted without code review. [S2]

6. A VERSION FINDING, AND THE OWNER REVERSING IT

While building the adapter the assistant found that Stripe's newest generally
available API version REMOVES a field the design had locked, replacing it with
one that has different semantics. The assistant's conservative choice was to pin
the PREVIOUS version, which supported every field the design sends.

THE OWNER'S REVIEW REVERSED THAT DECISION: a new integration uses the current
version, and card-only is expressed with the replacement field instead. Both
pins are the current version. Recorded because it is a case where the
conservative automated choice was the wrong product choice, and the owner's
judgement overrode it. The owner's review made five further corrections to the
provider boundary, including that the order's own snapshotted price and mode —
not the current configuration's — must be what is sent, so a configuration
change cannot re-price an order that is already open. [S2,S5]

7. VALIDATION (SOURCE-RECORDED) [S5]

Executed in a Linux cloud container. No Stripe network call at any point; the
adapter was driven entirely by deterministic doubles, and the signature verifier
by known-answer vectors.

  the full configuration matrix behaves as designed, including every
    fail-closed case
  the webhook configuration is READY with NO api key, NO price identifier and
    NO public web address present
  the selling configuration returns DISABLED BEFORE ANY SECRET IS READ
  the signature verifier passes every known-answer and negative vector
  an unexpected inbound API version is refused
  nothing is reachable from the internet
  full test suite  8,022 passed / 0 failed / 529 skipped across 211 files
                   (M13-1's baseline was 7,617)

Problems are reported by NAME ONLY — "api key missing", "price id malformed" —
never by value, length or key shape. [S5]
