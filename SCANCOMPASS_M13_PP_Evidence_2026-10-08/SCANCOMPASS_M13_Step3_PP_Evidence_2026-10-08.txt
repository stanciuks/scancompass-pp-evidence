2. PURPOSE

Let a signed-in account that has already proved it controls a hostname start a
real hosted payment for that hostname — and make it impossible for the browser
to influence anything commercial. [S2,S6]

3. THE BROWSER SENDS ONE FIELD

The request body is exactly one field: the domain. The schema is strict, so an
EXTRA KEY IS A REFUSAL rather than a silently ignored field. The browser
therefore cannot name an amount, a currency, a quantity, a tier, a price
identifier, a product, an account, an order or a return address, because no
such key parses. The account comes from the session cookie; everything
commercial comes from the server. [S2,S6]

Admission reuses the domain-verification sequence that M12C already had
reviewed, FACTORED OUT RATHER THAN COPIED, with two substitutions: the payment
gate and a payment-specific traffic bound. Copying it would have created a
second copy to keep correct. [S6]

4. EVERY REFUSAL HAPPENS BEFORE STRIPE IS CONTACTED

The order of the checks is the safety property. A refusal costs the customer
nothing; a Stripe object created by mistake costs a reconciliation.

  not signed in                     refused
  domain not canonical              refused
  no current M12C authorisation
  for that exact hostname           refused
  already owns a usable assessment
  for that hostname                 refused
  a previous payment for that
  hostname is awaiting a refund     refused, with DIFFERENT wording

EVERY ONE OF THESE HAPPENS INSIDE A DATABASE TRANSACTION, UNDER A LOCK ON THE
ACCOUNT ROW, BEFORE ANY NETWORK CALL. A refused checkout therefore creates no
Stripe object at all, and the acceptance proves it by asserting the provider
double recorded ZERO calls. [S2,S6]

The last two refusals are deliberately different sentences, because they mean
opposite things to the person reading them: one says you already own this, the
other says we owe you a refund first. A generic "you already have this" would
be false. [S2]

5. THE LOCK ORDER, AND WHY THE ROW IS RELEASED BEFORE THE NETWORK CALL

Every payment transaction locks the ACCOUNT row first. That is the fix for the
race the design review found at Step 0: it makes a checkout and a payment
arriving for the same account unable to interleave, so the checkout's read of
existing entitlements happens after any payment has committed rather than a
moment before.

Equally deliberate is what is NOT held: the transaction COMMITS BEFORE the
Stripe call. A row lock held across a network round trip would serialise an
account behind a provider timeout, and would also stall that account's incoming
payment messages. The acceptance proves both halves — that the lock is taken
before any eligibility read, and that it is free during the provider call.
[S2,S6]

A second property proved here is ADOPT, NEVER INSERT: if an open order for the
same target already exists, a second attempt adopts it and reuses the same
idempotency key, so the provider returns the SAME session rather than creating a
second payable one. Two concurrent requests for one target produce exactly one
order, with no deadlock and no database error surfaced to either caller. [S6]

6. AN HONEST TREATMENT OF "WE DO NOT KNOW"

The provider call has three possible answers and the distinction is the whole
safety property: a definite success, a definite refusal, and DON'T KNOW — a
timeout, a connection reset, an undocumented status. A don't-know answer may
mean a real payable session exists, so the order is deliberately NOT marked
failed; exactly one immediate retry is permitted with the same idempotency key,
and the slot stays occupied until the requested expiry has passed. Marking it
failed would free the slot while a customer could still pay. [S2,S6]

7. VALIDATION (SOURCE-RECORDED) [S6]

Executed in a Linux cloud container, with the concurrency cases against a
disposable PostgreSQL 18.6 database destroyed afterwards. The provider was a
deterministic double throughout; no Stripe network call was made.

  every refusal outcome behaves as designed, with the gate closed and open
  the account lock is taken before the entitlement read
  the lock is NOT held during the provider call
  the reconciliation blocker refuses with the provider double at ZERO calls
  adopt-not-insert, and a byte-stable idempotent request on retry
  the design review's race, replayed deterministically, now refuses correctly

Reflection prompts, carried forward UNANSWERED, to be written later in the
student's own words. NOTHING IN THIS FILE IS A REFLECTION.

  1. The browser is allowed to send one word: a domain name. What becomes
     impossible because of that, which a longer request would have made
     possible?
  2. Every refusal happens before Stripe is contacted. Who pays for a refusal
     that happens afterwards instead?
  3. When the provider's answer is "don't know", the system refuses to call the
     attempt failed. Why is admitting uncertainty safer here than picking the
     more likely answer?
  4. A database lock is deliberately released before the slow network call and
     re-taken afterwards. What would holding it have cost?
