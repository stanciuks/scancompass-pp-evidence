2. PURPOSE

Receive Stripe's messages about what actually happened to a payment, and turn
them into exactly one entitlement per payment — or, where a product cannot
honestly be delivered, into a visible obligation instead. [S2,S6]

3. THE SIGNATURE IS THE ENTIRE AUTHENTICATION

This route has no session, no cookie, no origin check and no cross-site token,
because Stripe is not a browser and holds none of them. The signature is
therefore all there is, which is why it is checked over the EXACT BYTES
RECEIVED — never a re-serialised copy — with a constant-time comparison, a
bounded header, and a five-minute timestamp tolerance in both directions.

A verification failure WRITES NOTHING. That is not cosmetic: if an unverified
body could append a ledger row, an unauthenticated caller could fill an
append-only table the application cannot delete from. [S2,S6]

4. PAID AND FULFILLED ARE ONE TRANSACTION, BY DECISION

There is deliberately no durable "paid but not yet fulfilled" state. The move
to paid, the creation of the entitlement and the recording of the event all
commit together or none of them do. The reasoning is recorded: a durable
paid-but-unfulfilled state is money taken with an obligation tracked nowhere,
and reconciling it would need a queue or a retry worker whose failure mode is
silent. Stripe already retries until it receives a success, and the application
only reports success AFTER the commit — so the retry mechanism exists and is
the provider's. [S2]

5. ARRIVAL ORDER IS NEVER ASSUMED, AND THAT IS THE HARD PART

Stripe does not guarantee the order its messages arrive in. A refund can
legitimately arrive BEFORE the payment it refunds. The naive handling —
acknowledge the refund as unmatched and move on — would let the payment arrive
later and grant a product for money that had already been returned.

The implemented behaviour instead: an uncorrelatable refund or dispute is
DEFERRED, with nothing written, so Stripe redelivers it. After a bounded window
it is recorded with its NORMALISED FINANCIAL EFFECT rather than its message
type, and any later payment for that same provider identifier consults that
record and refuses to grant. Storing the effect rather than the type is what
makes a one-off goodwill PARTIAL refund stop destroying a paid product while a
FULL refund still blocks it. [S2,S6]

The acceptance drives ELEVEN ordered-delivery cases and requires the final
state to be the same whichever order the messages arrive in — full refund then
payment, payment then full refund, partial refund first, and all three dispute
orderings. [S6]

6. THE HONEST FAILURE STATE: MONEY TAKEN, NO PRODUCT

One case cannot be made to come out well, and the design refuses to pretend
otherwise. If a payment arrives for a hostname whose single usable entitlement
already came from a DIFFERENT order, granting a second would break the central
invariant, and dropping the payment would lose real money.

So the payment is recorded durably, NO second product is granted, the order is
marked as requiring human reconciliation, and the message is acknowledged
because the fact is durable and retrying would change nothing. It also BLOCKS
further purchases for that hostname, so charges cannot accumulate against a
refund the operator already owes. A database audit query lists every row in
that state. No refund is issued automatically: that is a commercial decision and
an outbound money movement triggered by a provider message, which this project
will not do unattended. [S2]

7. TWO FINDINGS FROM THE OWNER'S REVIEW, AND HOW THEY WERE CLOSED

The implementation reported two residual issues rather than leaving them for
someone to discover. Both were closed on the owner's direction. [S2,S6]

A RACE NO ROW LOCK COULD CLOSE. Two transactions concerning the same payment
could, in a narrow window, both commit — granting a product despite a recorded
full refund — because they touch no row in common, so row locking cannot order
them. The fix is a transaction-scoped advisory lock keyed on the payment
identifier itself, taken as the transaction's FIRST statement, so the two are
serialised by the thing they actually share. The key is derived by hashing and
is never stored or compared.

AN EDGE LIMIT THAT WOULD HAVE REFUSED LEGITIMATE MESSAGES. The web server
configuration capped request bodies well below the size this route accepts, so a
large but legitimate Stripe message would have been rejected before the
application saw it. The repository's web-server template gained a dedicated
location for the webhook with the correct limit, its own traffic bound, and
refusals that tell Stripe to retry rather than to give up. IT IS A REPOSITORY
TEMPLATE ONLY — no live web server was read, tested or reloaded, and this
change is NOT installed on production. [S2,S6]
