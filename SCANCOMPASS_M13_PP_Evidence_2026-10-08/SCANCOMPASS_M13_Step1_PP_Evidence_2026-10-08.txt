2. PURPOSE

Give payments a durable shape before anything can write to it: the tables, the
keys, the constraints, the indexes and the database privileges, plus the
readiness check that proves the running image and the database agree about which
schema version they are on. [S2,S4]

3. WHAT WAS ADDED

Three tables in the project's dedicated database schema:

  payment_orders   one server-created purchase attempt, carrying the account,
                   the exact hostname, the state, the declared provider mode,
                   a snapshot of the configured price identifier, and the
                   expiry the server REQUESTED from the provider
  payment_events   an append-only ledger of provider messages, each recorded
                   with its own API version, its normalised financial effect
                   and a 32-byte digest of the exact bytes that verified
  entitlements     the source of truth: the only thing a future paid scan may
                   be admitted on

Schema contract moved from m12c-0003 to m13-0004; the migration ledger from
0000–0003 to 0000–0004. [S4]

4. THE PRIVILEGES ARE THE SECURITY PROPERTY, NOT THE CODE

The application database role was granted exactly what each table needs and
nothing more:

  payment_orders   SELECT, INSERT, UPDATE  — and NO DELETE
  payment_events   SELECT, INSERT          — and NO UPDATE, NO DELETE
  entitlements     SELECT, INSERT, UPDATE  — and NO DELETE

"Append-only" is therefore enforced by the database, not by code discipline: a
recorded provider event cannot be rewritten even by a defect in the
application. A financial record is not the application's to remove, and the
absence of the privilege is what makes that true rather than merely intended.
The disposable-database acceptance proves the refusals by attempting them. [S4]

A deliberate omission is recorded as a decision: there is NO foreign key from
an entitlement to a domain authorisation. A cascade would destroy a paid
entitlement when a user removes a domain, and a restriction would stop a user
removing their own domain because they once bought something. Both are wrong,
so authorisation is re-established by CALLING the M12C check at use, never by a
referential link. [S2]

5. TWO DEFECTS THE DATABASE FOUND BY BEING RUN

This is the most useful evidence in the step, because both defects were in the
DESIGN and only appeared when real PostgreSQL executed it. [S4]

SQL'S THREE-VALUED LOGIC ACCEPTED WHAT THE DESIGN SAID IT REFUSED. Two
coherence constraints were written as comparisons such as "reversal kind equals
REFUND". A CHECK constraint PASSES when its expression evaluates to NULL, and a
comparison against NULL is NULL — so a refunded order with NO reversal kind
recorded evaluated to NULL and WAS ACCEPTED. That is precisely the "reversed
order with no kind" the design's own prose said was impossible. Real PostgreSQL
18.6 accepted the row in the acceptance run. Both constraints now guard each
comparison with an explicit not-null test, which is a strict tightening that
makes the database enforce exactly the stated rule. The same hole existed on the
entitlement table's termination reason and was corrected the same way. [S4]

THE ROLLBACK ERA RULE WAS TOO GENEROUS. The merged design's test for "no
payment activity has ever happened here" excluded orders whose checkout had
failed. That was wrong: a failed-looking order can stand for a Stripe session
that really existed and could have been paid moments before it expired, with the
message still in flight. The rule now requires all three payment tables to be
completely empty. [S2,S4]

The owner's review of this pull request made four further corrections, the
sharpest being that every order in a money-taken state must carry a provider
payment identifier, so a reversal can always find the order it belongs to. [S2]

Reflection prompts, carried forward UNANSWERED, to be written later in the
student's own words. NOTHING IN THIS FILE IS A REFLECTION.

  1. The application is not allowed to delete a payment row, and that is
     enforced by the database rather than by the program. Why is removing the
     ability better than deciding not to use it?
  2. A constraint that was supposed to reject bad data accepted it, because a
     comparison with an empty value is neither true nor false. What does that
     say about trusting a rule you have written but never executed?
  3. The rule for "no payment has ever happened here" was deliberately made
     stricter than seemed necessary. What would the cost of being wrong in the
     other direction have been?
