2. PURPOSE

Decide, before any code existed, exactly what is being sold, what the database
must hold, who is allowed to decide what, and what must be true for a payment
never to produce either a lost purchase or a free product. The output is one
authoritative design document that every later slice is checked against. [S2]

3. WHAT ONE PURCHASE IS, DECIDED HERE

An Extended Security Assessment is a ONE-TIME purchase that buys exactly one
future completed extended assessment, for ONE EXACT HOSTNAME, for the
authenticated account that paid. Ninety days of unused life from the moment
payment is confirmed. Card only, euro, quantity fixed at one on the server.

It is deliberately NOT a subscription, NOT a credit balance, NOT a bundle, NOT
transferable, NOT ownership verification, and NOT permission to scan an
arbitrary host. Buying for a domain buys nothing for its subdomains, and that
narrow reading is a decision rather than an oversight. [S2]

4. THE DECISION THAT MATTERS MOST

A table in the design assigns every decision to exactly one authority, and the
right-hand column is the point:

  which account is buying      the session cookie — never the request body,
                               a header, or any Stripe field
  which hostname               the request body's domain, canonicalised, AND a
                               current M12C authorisation — never Stripe
                               metadata
  which product, which price   compiled-in code and operator configuration —
                               never the browser, under any circumstances
  that a payment happened      a signature-verified Stripe event cross-checked
                               against the server's own order — never a
                               browser returning to a success page
  that a payment has NOT been
  reversed                     our own ledger, read inside the deciding
                               transaction — never the mere ABSENCE of a
                               reversal message, which may simply not have
                               arrived yet

The last row is the one a first draft got wrong, and section 5 explains why.
[S2]

5. NINE ISSUES FOUND BY INDEPENDENT REVIEW, AND WHY THAT IS THE EVIDENCE

The design was reviewed twice before any code was written. SEVEN issues were
found in the first pass and TWO more in the second, and the document records
what each section claimed before, why it was wrong, and where the corrected
answer now lives. Nothing was quietly rewritten to look as though it had always
been right. [S2,S3]

The most serious was a genuine time-of-check-to-time-of-use race that broke the
design's central invariant. The first draft claimed that "at most one usable
entitlement per account and hostname" held "by construction". Review produced
the exact schedule that breaks it: a payment transaction inserting an
entitlement, a checkout transaction reading entitlements a moment earlier and
seeing none, and then the checkout's insert succeeding precisely because the
first transaction had committed in between. The database index the draft relied
on serialised ORDERS against ORDERS and never serialised the ENTITLEMENT READ.
The fix is to serialise every payment transaction on the account row first, so
the read happens after the commit, with the index kept only as a backstop that
correct code never reaches. [S2]

Four of the other eight are worth naming because each is a class of mistake
rather than a typo:

  - a stale-checkout cleanup rule keyed on row AGE could have freed a slot
    while a real, still-payable Stripe session existed, allowing two
    simultaneously payable sessions. It is now keyed on the expiry the server
    actually requested, written down BEFORE the provider is called;
  - webhook delivery ORDER had been assumed. Stripe does not guarantee it, so a
    refund arriving before the payment it refunds had to be handled without
    acknowledging it as final. The corrected design defers such a message,
    records its normalised financial effect after a bounded window, and has
    later payments consult that record;
  - rollback had been described for one era only. Before any payment exists, an
    older image is a safe rollback; after payment activity exists, an older
    image has no webhook route, so every refund and dispute message Stripe
    sends fails and is eventually LOST. The design now names a rollback floor;
  - a paid-but-unreconciled payment did not block a repeat purchase, so a
    customer owed a refund could be charged again.

WHY THIS IS GOOD EVIDENCE RATHER THAN EMBARRASSING. Every one of these was
found and fixed while the cost was a paragraph. Had the TOCTOU race shipped, the
symptom would have been two usable purchases for one payment, discovered by a
customer. The review passes are recorded in the design's own correction log and
are the reason the later slices had a specification worth checking against.
