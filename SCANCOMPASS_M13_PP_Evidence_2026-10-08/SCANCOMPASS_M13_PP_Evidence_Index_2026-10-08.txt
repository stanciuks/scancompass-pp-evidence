1. WHAT M13 IS, IN ONE PARAGRAPH

M13 builds the commercial half of the product: a one-time purchase called an
Extended Security Assessment, for one exact hostname the account has already
proved it controls, recorded as orders, provider events and entitlements in the
database. It does NOT build the extended scanner, does not consume an
entitlement, and adds no paid scan route — that is M14. The central safety
property is that an entitlement row is the ONLY thing a future scan may be
admitted on, and that no Stripe object, message or metadata field is ever
treated as authority for which account or which hostname a payment was for.
[S2]

4. WHY THIS MILESTONE WAS BUILT THE WAY IT WAS

Three decisions shape the whole milestone and are worth stating once here
rather than six times.

PAYMENT IS NOT PERMISSION. A purchase is only possible for a hostname the
account has already verified through M12C, and M14 must re-check that proof
again at the moment the entitlement is used. Money never substitutes for
ownership. [S2]

NO STRIPE FIELD IS AUTHORITY. A verified webhook proves a message came from
Stripe; it does not prove which account or which hostname the payment was for.
Those two facts are read only from the order row the server itself created.
[S2]

CLOSED BY DEFAULT, AND SPLIT IN TWO. Payments are off unless an operator turns
them on, and the configuration is split so that "stop selling, keep
reconciling" is structural: selling can be switched off while refunds and
disputes for past purchases are still recorded. Production ran with payments
off for the whole of M13. [S2]

5. THE SHAPE OF THE EVIDENCE, AND ONE DELIBERATE ASYMMETRY

Slices 0 to 4 are SOURCE-ONLY work: every Stripe interaction in them is a
deterministic local double or a locally signed fixture, and each note says so.
Slice 5 is the only one with real provider contact, and it is also the only one
with owner-observed actions, because only the owner may sign in to Stripe, pay
a hosted checkout in a browser, or issue a refund.

That asymmetry is the reason the M13-5 note is the longest in the package and
the only one carrying an [R1] label.

A SECOND ASYMMETRY, RECORDED SO A LATER READER DOES NOT MISREAD A TEST COUNT.
Slices 0 to 4 ran in a Linux cloud container and report 0 test failures. Slice
5 ran on the owner's macOS workstation, because it needed the owner's browser
and the Stripe command-line tool, and it reports 8 failures — the same 8
platform-specific failures in one deployment-package test file that the R1 note
already records, in a file M13 never touches. The Linux continuous-integration
run on the exact merge commit is the authority, and it is green. [S1,S7]

6. WHAT REMAINED INTENTIONALLY UNFINISHED

Carried honestly rather than quietly closed. Each is expanded in the M13-5
note.

  - M13-6 has not started: the rollback floor, the era-2 reconciliation
    procedure, the production runbook, and two explicitly separate deployment
    decisions — deploying migration 0004 with payments disabled, and only
    later enabling payments — neither of which has been taken;
  - every live-mode blocker remains open, including the final price, tax
    treatment, published refund wording, a live restricted key, a live webhook
    endpoint pinned to the expected API version, a verified pre-change backup,
    and a monitoring owner for the two reconciliation queues;
  - the two payment readiness statuses exist but NOTHING SURFACES THEM — no
    boot log line and no health field — so "watched" has no mechanism yet;
  - a provider-first deferred reversal was not practically exercised against
    real Stripe, because provider delivery order is nondeterministic;
  - the three-hour stale-checkout sweep timing was not exercised in real time;
    the provider's own session-expiry path was;
  - no dispute was exercised, because a chargeback cannot be raised on demand;
  - no completed anonymous free scan was exercised in the disposable
    acceptance environment.
