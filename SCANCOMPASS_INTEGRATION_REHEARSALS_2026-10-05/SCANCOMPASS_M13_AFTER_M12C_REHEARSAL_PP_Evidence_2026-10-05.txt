2. THE CENTRAL FINDING: A PAYMENT ASSUMPTION HAD GONE OBSOLETE

PR #15 was written BEFORE M12C existed, and it had to assume what a domain
authorisation would eventually mean. It assumed the paid object is a
REGISTRABLE DOMAIN — that buying example.com covers www.example.com and
shop.example.com, and that a subdomain input would be refused or folded into
its parent.

M12C then chose the opposite, deliberately: authorisation is for ONE EXACT
CANONICAL HOSTNAME and grants nothing on a parent or a child.

The product documentation was checked rather than guessed at. An older section
does say "per registrable domain", but a newer M12C section records that this
was NARROWED to the exact canonical hostname, and the canonical-domain module
states it. NO DOCUMENT REQUIRES a paid assessment to cover a registrable
domain, so nothing needed escalating, and the narrower, fail-closed reading was
chosen.

ADOPTED SEMANTICS: a paid assessment is purchased for, and admitted for, the
exact canonical hostname the authenticated account is CURRENTLY authorised for.
The payment layer's domain type IS M12C's canonical type — no second brand was
invented. Checkout canonicalises with M12C's own parser, exactly as M12C's
routes do; admission REFUSES an alias rather than correcting it, mirroring the
authorisation check. Both payment domain columns carry M12C's storage-shape
constraint, so a payment row can never hold a value that could not equal an
M12C domain.

Proven against a real database with real M12C rows: an authorisation for
shop.example.com cannot buy example.com, www.shop.example.com,
www.example.com or blog.example.com; an example.com authorisation cannot buy
www.example.com; an entitlement for a subdomain admits nothing for its parent.
A tenant under a private suffix is its own identity, while the suffix itself is
refused. Internationalised and uppercase spellings resolve to one identity;
schemes, paths, ports, credentials, whitespace and public suffixes are refused
rather than stripped.

3. NINE OTHER OBSOLETE ASSUMPTIONS, AND WHAT EACH BECAME

  - the older "per registrable domain" rule was taken as governing; it is
    superseded by the M12C narrowing;
  - the eligibility check always answered "not integrated"; it now calls
    M12C's real authorisation check;
  - M12C would return an authorisationId — see section 4;
  - the eligibility query carries a time value from the caller — see section 5;
  - eligibility has two outcomes, and a database failure is "not eligible or
    thrown". M12C has a THIRD, an explicit unavailable outcome, now mapped to a
    503 response rather than being silently treated as a refusal;
  - the payment migration is 0003 — M12C owns 0003; see section 6;
  - a restrict-violation foreign key raises one SQLSTATE. True on the
    PostgreSQL 16.14 the draft was written against; PostgreSQL 18.6 raises a
    DIFFERENT code for RESTRICT than for NO ACTION. Confirmed directly on 18.6
    and the test corrected;
  - the migration ledger can be checked with a prefix slice plus a loose
    pattern; replaced by exact lists;
  - the draft's database acceptance ran on PostgreSQL 16.14; it was re-run on
    18.6, the production major version.

4. authorizationId WAS REMOVED, NOT INVENTED

The draft threaded an authorisation identifier from the eligibility check
through to the admission result. M12C's rows are keyed by (account, domain)
with NO SURROGATE IDENTIFIER, so there was nothing to supply.

Every use was audited: NO COLUMN, ORDER, EVENT, PROVIDER REQUEST OR COMPARISON
EVER USED IT. It was therefore REMOVED rather than replaced, and nothing was
invented to fill it. If provenance is needed later, M12C's own authorised
answer already carries the method, the verification time and the expiry.

5. NO STALE CALLER TIME, AND WHERE AUTHORISATION IS RECHECKED

The draft passed a time value from the caller into eligibility and admission.
Accepting it would have undone the exact correction M12C had just made for the
same class of defect, so it was removed:

  - NO TIME REACHES THE AUTHORISATION CHECK. Admission no longer takes one, and
    its entitlement half reads a clock AFTER the M12C decision returns;
  - checkout's own time value remains, but only for payment bookkeeping —
    order timestamps, session expiry, the open-order window;
  - the M12C feature gate is not consulted by payment, matching M12C's
    contract that the gate neither grants nor removes authority.

WHERE AUTHORISATION IS CHECKED, AND WHY THAT PLACEMENT:

  - CHECKOUT asks M12C before writing anything, and the answer IS NOT STORED;
  - FULFILMENT — the provider webhook — DOES NOT consult authorisation at all.
    A verified payment is recorded as A FACT ABOUT MONEY. If the domain
    authorisation expired between checkout and the webhook, THE WEBHOOK STILL
    RECORDS A VALID FINANCIAL EVENT, because money did change hands and
    pretending otherwise would lose a real record;
  - ADMISSION asks M12C AGAIN at the moment the paid assessment is actually
    used. Payment alone never admits.

That separation is the interesting part of this reconciliation: the financial
record and the authority to act are deliberately allowed to disagree, and the
check that matters happens at use. It was tested directly — an authorisation
lapsing between checkout and webhook leaves the payment recorded and the
admission refused, restored only by a fresh M12C proof, and refused again once
the account is disabled.

Payment does not read the authorisation tables; it imports only M12C's
canonical-domain module, a type-only identity module and the authorisation
check itself. M12C imports nothing from payment. Both directions are pinned by
boundary tests.

6. THE PAYMENT MIGRATION WAS REGENERATED AS 0004, NOT RENAMED

M12C owns 0003, so the provisional payment migration had to move. It was NOT
hand-renamed. The M12C snapshot and journal were restored from the base, the
provisional file deleted, the schema resolved, and the migration GENERATED
afresh by the tool — producing 0004 with a snapshot whose previous-identifier
field points at M12C's, and a journal entry at index 4. A second generation run
reported no schema changes, which is the check that the committed state and the
declared schema agree.

Migrations 0000 through 0003 are byte-identical to the base, with their
checksums unchanged. The generated 0004 differs from the provisional file only
by two added storage-shape constraints. The schema contract label moved to
m13-0004. The combined schema reaches 17 tables.

7. CONFLICTS, AND THREE DEFECTS THAT MERGED SILENTLY

Applying the payment branch produced 19 CONFLICTED FILES, resolved textually in
one commit so the chronology stays reviewable. The resolutions were unions
where both sides added, and the BASE's stricter form where the two disagreed —
for example the base's exact ledger list was kept and extended rather than
accepting the payment branch's looser pattern.

More interesting are the three defects that produced NO CONFLICT AT ALL and
were wrong anyway. They were found by the first gate run, not by the merge:

  1. both branches had added the same variable name in the same scope of one
     test file. The merge kept BOTH, giving a compile error for a redeclared
     block-scoped variable;
  2. three tests asserting "this milestone changed no migration" used a
     three-item slice that silently met M12C's four-entry list, giving three
     failures. Restored to the exact-list form and extended;
  3. a policy test still read the deleted provisional migration file by name,
     failing the whole suite.

A clean automatic merge is not a correct one. That is the lesson this section
exists to record.

8.1 AN ACCEPTANCE RUNNER STARTUP DEFECT WAS DISCOVERED HERE

The acceptance runner refused to start on PostgreSQL 18.6 with a WRONG VERSION
verdict, on five of six attempts. Reproduced by hand and traced: the official
image's entrypoint initialises a new cluster by starting a TEMPORARY server,
creating the database, stopping it, and only then starting the real one. The
runner's readiness probe answered from the temporary server, and the single
version query that followed landed in a window where it could not connect — and
the runner reported ANY failure of that query as a version fact.

NO UNMODIFIED RUN REACHED A PASS, on the rehearsal tree OR on the base, which
is how it was classified as pre-existing rather than caused by this work. With
a local, uncommitted readiness patch the rehearsal tree's database phases all
passed — 34 account acceptance, the restart child, 30 restore drill, and 452
across the guarded suites — with the verdict still failing on the hermetic
phase alone, because of two wall-clock-dependent tests that also fail on the
base. The patch was removed from both trees. BOTH DEFECTS WERE FIXED
AFTERWARDS IN THEIR OWN SEPARATE CHANGE; see the baseline reliability record.
